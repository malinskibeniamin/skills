让跟踪器中的问题按照由分诊角色组成的小型状态机流转。

当仓库将外部拉取请求视为请求入口时（参见跟踪器配置），分诊也涵盖这些请求：**PR 是附带代码的问题**——角色相同、状态相同、状态机相同，差异会在下文以“对于 PR”标出。根据跟踪器将单独的 `#42` 解析为问题或 PR。

探索代码库时，使用项目领域术语表，确保标题、评论和智能体简报与项目语言一致。遵循受影响区域的 ADR。使用 `/read-the-damn-docs` 了解外部或当前行为，使用 `/plan-arbiter` 在相互竞争的修复方案之间作出选择，并对大型史诗任务使用 `/visual-plan`。

## AI 免责声明

分诊期间发布到跟踪器的每条评论都**必须**以以下内容开头：

```
> *This was generated by AI during triage.*
```

## 问题跟踪器

通过 `git remote -v` 和仓库约定进行检测：

- **GitHub**（远程地址为 `github.com`）-> 使用 [`gh`](https://github.com/malinskibeniamin/skills/blob/main/triage/tracker-github.md)
- **Jira**（分支或提交中包含 Atlassian 风格的工单 ID，或者存在 `.atlassian/` 配置）-> 使用 [`acli`](https://github.com/malinskibeniamin/skills/blob/main/triage/tracker-jira.md)

两者都存在（GitHub 仓库 + Jira 工单）-> 询问用户希望在哪一个系统中创建或分诊。

## 角色

两个**类别**角色：

- `bug`——某项功能出现故障
- `enhancement`——新功能或改进

五个**状态**角色：

- `needs-triage`——需要维护者评估
- `needs-info`——等待报告者提供更多信息
- `ready-for-agent`——已完整说明，可供无人值守的智能体处理
- `ready-for-human`——需要人工实现
- `wontfix`——不会处理

每个已分诊的问题必须恰好包含一个类别角色和一个状态角色。状态冲突时 -> 标记冲突并在操作前询问。

以上为规范角色名称。跟踪器中的实际标签或状态字符串可能不同——如果不同，则根据项目中已有的标签或状态进行推断，询问一次，并在当前会话中记住。

## 显示需要关注的内容

查询跟踪器。按从旧到新的顺序展示以下三个分组：

1. **无标签 / 无状态**——从未分诊
2. **`needs-triage`**——正在评估
3. **自上次分诊记录以来报告者有新活动的 `needs-info`**——需要重新评估

如果 PR 在范围内 -> 将外部 PR 纳入这些分组，并在每一行标记 `[PR]` 或 `[issue]`。发现过程只展示*外部* PR（由跟踪器配置定义哪些人属于外部人员）——协作者正在处理的 PR 不属于分诊工作。该筛选仅适用于发现过程；无论作者是谁，明确指定的 PR 始终需要分诊。

显示数量以及每一项的单行摘要。让维护者选择。

## 分诊特定问题或 PR

1. **收集上下文。** 阅读完整的问题或 PR（正文、评论、标签或状态、报告者、日期；对于 PR，还要阅读差异）。解析之前的分诊记录，避免再次询问已解决的问题。使用项目领域术语表探索代码库，并遵循相关区域的 ADR。执行两项代码库检查：(a) **冗余性**——按领域概念（而不仅仅是请求中的措辞）搜索请求行为的现有实现，并报告检查过的位置；如果找到 -> 作为已实现的 `wontfix` 处理（第 5 步）。(b) **先前拒绝记录**——阅读 `.out-of-scope/*.md`，指出与此请求相似的内容。

2. **提出建议。** 告知维护者建议的类别和状态及其理由，并提供与请求相关的简短代码库摘要——包括是否已经实现。等待指示。

3. **验证主张。** 在深入追问前，检查主张是否成立。对于错误 -> 按照报告者提供的步骤复现。对于 PR -> 确认差异是否实现了其声明的功能：检出代码，运行相关测试或命令。报告结果——已通过代码路径确认、验证失败或信息不足（强烈表明应设为 `needs-info`）。经过确认的验证结果能显著增强智能体简报。有关根因调查和 TDD 修复计划，请参阅 [REFERENCE.md#tdd-fix-plan-mode](https://github.com/malinskibeniamin/skills/blob/main/triage/REFERENCE.md)。

4. **深入追问（如需要）。** 如果问题需要进一步完善 -> 当领域语言或 ADR 至关重要时，运行 `/grilling`。

5. **应用处理结果：**
   - `ready-for-agent` -> 发布智能体简报评论（[AGENT-BRIEF.md](https://github.com/malinskibeniamin/skills/blob/main/triage/AGENT-BRIEF.md)）
   - `ready-for-human` -> 使用相同结构，但注明无法委派的原因
   - `needs-info` -> 发布分诊记录（参见 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/triage/REFERENCE.md)）
   - `wontfix`（已实现）-> 指明它在代码库中的位置；**不要**写入 `.out-of-scope/`（该知识库用于记录*被拒绝*的请求，而不是已经构建的功能），然后关闭
   - `wontfix`（错误）-> 礼貌说明原因，然后关闭
   - `wontfix`（增强功能）-> 写入 `.out-of-scope/`，在评论中添加链接，然后关闭（[OUT-OF-SCOPE.md](https://github.com/malinskibeniamin/skills/blob/main/triage/OUT-OF-SCOPE.md)）
   - `needs-triage` -> 应用角色；如果已有部分进展，可以选择添加评论

## 快速覆盖状态

用户说“将 #42 移至 ready-for-agent” -> 信任用户，确认即将执行的操作（角色变更、评论、关闭），然后执行。跳过深入追问。如果未经过深入追问会话便移至 `ready-for-agent`，询问是否需要编写智能体简报。

## 恢复之前的会话

如果问题中存在之前的分诊记录 -> 阅读这些记录，检查报告者是否回答了尚未解决的问题，并在继续前展示更新后的情况。不要再次询问已解决的问题。
