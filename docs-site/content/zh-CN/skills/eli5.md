向对此一无所知的人解释该主题。将请求内容作为主题；
明确调用时，将 `$ARGUMENTS` 视为权威依据。

## 约定

1. 简化之前，先用证据支撑解释。对于模块、权衡取舍或事故，应检查相关源
   材料。对于外部事实，优先采用最新的一手来源。绝不能为了让叙述更简洁而
   编造因果环节。分别标明事实与推断，包括重要的不确定性。
2. 选择一个能够保留重要事实的思维模型。尽可能去除术语；
   对于无法避免的术语，在图示旁用通俗语言加以定义。
3. 创建一个自包含的 HTML 产物：以大幅图示为主、文字为辅，不能只是
   用图标装饰的长篇文章。
4. 依据证据核验解释，然后检查产物在宽视口和窄视口下的渲染效果。

## 受众

假设受众没有相关主题知识，而不是智力不足。使用熟悉的事物、具体的动词
和沉稳的成人语气。绝不能显得幼稚或居高临下。如果省略某个细节会导致
结论逆转，则保留该细节；否则将其放入来源说明中。

仅当范围选择错误会使图解产生误导时，才提出一个简短问题。
否则，选择最小的实用范围，低调说明假设，然后继续。

## 视觉语法

- 优先使用三到六个场景。每个场景或面板只表达一个概念，并提供清晰的阅读顺序。
- 使用大型图示、空间关系、运动路径、时间线、比例尺或前后状态。
  装饰性图片不计算在内。
- 主线内容仅使用简短的标题和标签。避免使用段落。让视觉元素承载
  顺序、数量、归属和因果关系。
- 对于模块，展示输入 -> 转换 -> 输出。对于权衡取舍，展示获得了什么
  以及失去了什么。对于事故，展示触发因素 -> 传播过程 -> 影响 -> 恢复过程，并以不同方式
  标记事实与推断。
- 最后用一幅图和一句话重申核心思维模型。

## HTML 产物

- 使用语义化 HTML、内联 CSS 和 SVG。将所有必需的样式、图片和脚本都保存在
  文件中；不得依赖 CDN、远程字体、图片外链或构建步骤。
- 转义不受信任的源文本，不要插入原始 HTML。
- 确保布局具备响应式、高对比度，并且在没有动画的情况下仍清晰可读。遵循
  `prefers-reduced-motion`；不要禁用用户缩放，也不要仅依靠颜色传达信息。
- 在窄屏下，将横向图示重新排版为纵向堆叠的场景，而不是不断缩小
  标签直至无法阅读。
- 为每个有意义的视觉元素提供文本替代内容或无障碍说明。使用简洁的
  可见标签，并配合 `aria-labelledby`、`<figcaption>` 或同等语义方式。
- 将引用、文件位置、假设和必要的细节放入名为“来源和假设”的紧凑
  `<details>` 区域中，使图片叙事保持简洁。
- 仅当交互能够显著提升理解时，才添加内联 JavaScript。静态
  产物仍必须能够传达核心解释。

如果宿主提供原生 HTML 产物展示界面，请使用该界面。否则，将文件写入
宿主原生的临时目录，例如使用
`mktemp -d "${TMPDIR:-/tmp}/eli5.XXXXXX"` 创建的目录；不要将一次性图解添加到代码仓库中。

## 验证并返回

通过隔离的浏览器或宿主预览打开结果，绝不能使用人类用户自己的浏览器。
检查首屏是否清楚传达主题、标签是否被裁切、视觉内容在窄屏上是否仍清晰可辨，
以及每项事实或因果声明是否都与源材料一致。修复缺陷后再返回。

返回产物或其绝对路径、一句总结性结论，以及所有重要的
不确定性。不要在聊天中重复完整解释。
