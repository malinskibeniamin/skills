当下文工作流需要模型可调用的技能时，请为每个依赖分别调用 Skill 工具。没有该工具的宿主应按[依赖加载规则](https://github.com/malinskibeniamin/skills/blob/main/writing-for-agents/SKILL-MECHANICS.md#loading-dependencies)完整读取规范 `SKILL.md`。仅供用户调用的技能应推荐给用户，不要自动调用。

你已获得一份规格。该规格应关联若干工单，描述如何实现它。

仅为已批准、具有真实阻塞依赖且工单可独立验证的规格选择此技能，不用于普通的单工单任务。用户调用此技能即表示明确要求委派并使用并行智能体；加载或提及此技能不代表同意委派。

如果存在 `CLAUDE.md`，先读取 `CLAUDE.md`；否则读取 `AGENTS.md`。按照其中的问题跟踪器指引操作。如果没有，请告诉用户运行 `/work-automation-kit`。

目标是在单个**集成分支**上实现整个规格，并按问题跟踪器关闭工作的方式解决每个工单。

工单不是步骤列表，而是带有阻塞关系的**任务图**。这意味着总有一个由已就绪工单组成的**前沿**可供领取。

与子智能体之间的沟通应当简洁。主要通过**上下文指针**沟通：指向规格、工单、研究笔记和先前的提交。不要重复通过指针即可获得的信息。

尽可能在后台运行**实现子智能体**，以获得**最大并发度**。

## 步骤

1. 阅读规格和工单。阅读到足以理解任务图为止。

2. （可选）使用**探索子智能体**完成工单所需的探索——相关代码文件或外部文档。确保探索子智能体可以保存文件——它应将 Markdown 笔记保存在仓库外、所有后续子智能体都能访问的目录中。这让**实现子智能体**专注于实现而非探索。

3. 创建集成分支。如果问题跟踪器通过 PR 关闭工作，或用户要求 PR，则在第 5 步首次合并后打开草稿 PR（没有领先 main 的提交的分支无法打开 PR），并标记为关闭该规格和工单。

4. 使用**实现子智能体**实现每个工单，每个子智能体在各自的工作树和分支上工作。每个实现子智能体：
   - 开始前确认其工作树基于集成分支，如果不是则重置到集成分支上；
   - 调用 Skill 工具并传入 "tdd" 来构建该工单；
   - 报告完成前将集成分支的最新提交合并到自己的分支，使第 5 步成为快进合并。

5. **实现子智能体**完成后，由**合并子智能体**将其工作合并到集成分支。

6. 如果这改变了可用工单的**前沿**，就为新工单启动更多**实现子智能体**。这样可以实现最大并发度。

7. 所有工单完成后，调用 Skill 工具并传入 "review"，审查集成分支。在单个**实现子智能体**中修复代码审查提出的所有问题。

8. 如果已有草稿 PR，而用户要求的终点是草稿，就保持草稿状态；否则标记为可供审查。没有 PR 时，按问题跟踪器关闭工作的方式解决每个工单，并报告集成分支。

9. 清理所有**实现子智能体**的工作树。
