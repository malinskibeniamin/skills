从一个维度审查：现在做这项工作是否合适，规模是否恰当？正确性仍由
`/review` 负责；这个视角关注谁会受益、我们如何确认，以及持续维护的成本。
[RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ss/RULES.md) 收录了所有规则及其等级，以及按时效性加权的支持证据。

## 类别 [#buckets]

每个 PR 只能归属一个主要类别。混合目的应拆分为不同的 PR。

| 类别 | 主张 | 支持该主张的证据 |
| --- | --- | --- |
| 维持运行 | 节省资金，消除重复性劳动或风险 | 事故、告警、发现的问题、弃用日期、金额、重复性劳动耗时 |
| 体验改善 | CI、开发者体验、性能、声誉 | 改进前后的测量结果、为谁消除了阻碍、发生频率 |
| 功能 | 带来收入 | 明确的客户、潜在客户、细分市场、发布或演示；收入实现路径 |
| 设计押注 | 通过设计判断降低未来成本 | 减少概念、移除功能或接口、可逆切片、决定保留或放弃的信号 |

## 流程 [#procedure]

1. **理解意图：**阅读 PR 正文、关联工单、提交记录和差异统计。记录其声称所属的类别；
   如果没有说明，则推断类别，并标明缺少这一主张。
2. **受益者：**明确用户画像或客户，以及他们将获得什么改变。仅写“用户”或
   “清理”并未明确受益者。
3. **为何现在做：**找出触发因素（事故、客户请求、发布日期、交易、成本激增、
   经测量确认的性能退化）。没有触发因素，就意味着这项工作在与路线图争夺资源；应明确指出。
4. **证据等级：**实测 > 明确指认 > 合理推测 > 单纯断言。有关性能、成本和
   可靠性的主张需要数据；假设被证伪时，应关闭 PR。
5. **可触达性：**追踪价值是否能通过受益者今天就能使用的入口实现：UI、API、
   CLI、文档，或在某处已启用的功能开关。已合并但无法触达的变更尚未产生价值。
6. **持续维护成本：**以金额计的运行成本、新增基础设施、配置项、功能开关、值班负担、
   审查负担。删除和简化也算价值。
7. **切片：**采用能验证主张的最小可逆增量；默认关闭；后续工作
   单独建工单，不并入当前变更；从设计上保障现有付费客户不受影响。
8. **应用规则：**检查 RULES.md 中与该类别和涉及范围相符的条目。

## 结论 [#verdict]

- **理由充分**：类别、受益者和证据相互吻合；切片规模适当。
- **需要补充理由**：可能有价值，但 PR 未能体现。要求补充那一项
  缺失的事实（受益者、触发因素、数据或验收标准），而不是长篇说明。
- **不太可能获得回报**：没有受益者、没有触发因素、成本超过合理预期的回报，或
  唯一理由是未经测量的主张。建议推迟、缩小范围或关闭。

绝不只因审美偏好而阻止合并。价值由负责人判断；这个视角让取舍
清晰可见。如果 PR 明确了后续工作，截止日期可以成为接受粗略切片的理由。

## 严重程度 [#severity]

- **P1 价值问题**：合并很可能造成资金或信任损失：漏计费或重复收费、
  已配置却未生效的付费功能或安全功能、影响现有客户的破坏性变更、
  未经产品负责人批准的收入或定价变更、为未经验证的需求做出不可逆决策。
- **P2 价值问题**：缺少受益者、触发因素、证据、验收标准或可触达性；PR 规模过大或
  混合多个目的；新增持续性成本却未提供金额；只有一个使用者却追求通用性。
- **P3**：措辞或工单规范问题。仅在摘要中提及。

## 自动审查 [#automated-review]

在自动审查流程中：仅当结论不是
**理由充分**时，发布一条顶层价值评论，最多列出三个问题，每个问题包含缺失的事实和一行修复建议。
不发表评论表示价值论证清晰。不要向作者复述 PR 内容。

## 输出 [#output]

```md
Value: <bucket> | Beneficiary: <who> | Trigger: <why now> | Evidence: <grade>
Verdict: justified | needs justification | unlikely to pay off
- [P1|P2 Value] <rule id> <gap> - <consequence> - <smallest fix>
```

本审查角色的输出上限为 250 词。没有问题时，只输出前两行。
