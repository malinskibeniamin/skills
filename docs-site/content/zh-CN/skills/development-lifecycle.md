负责一个结果，并持续推进，直到证据证明目标已实现，或出现真正的阻碍。

## 结果契约

编辑前，从请求和仓库中提取以下四项：

- **目标**：高级最终状态。
- **约束**：无法推断的仓库限制、保留给用户的决策，以及
  不可逆的边界。
- **验证**：能够区分真正完成与表面可行的可执行检查或可观察行为。
- **停止条件**：请求的终点，以及确实需要用户介入的条件。

不要将其扩展为对代码的预测或冗长的流程。范围明确的构建、修复或
实现请求即授权执行：简要说明契约，然后立即继续。

## 执行循环

**检查 -> 操作 -> 验证 -> 重复。**

### 检查

- 找出最可能导致方案失效的盲点。
- 阅读代码、测试、日志、当前文档和相邻示例。优先采用可执行的
  证据，而不是另一份文字摘要。
- 首先解决变化可能性最高的未知项。将其余项分类为查阅、原型验证、
  可逆假设或暂停触发条件。
- 遵循现有惯用方式和已验证的规模。只有当观察到的任务进入某个独立领域时，
  才加载相应的专业指导。

### 操作

- 由一个主模型全权负责。委派和持续的后台工作需要
  用户明确授权。
- 从最小且显而易见的改动开始。优先删除或复用，再考虑增加机制。
- 对于缺陷和重要行为，在公开契约层面使用 TDD：RED -> 最小 GREEN
  -> REFACTOR。不要为静态连接或保持行为不变的删除强行编写测试。
- 让发现结果修正方案。重新规划受影响的部分，不要机械遵循过时的
  预测。
- 严守目标范围。除非相邻清理工作会阻碍验证，否则仅将其作为问题报告。

### 验证

- 运行仓库中适用的测试、类型检查、代码检查、构建和静态检查。
- 通过实际入口验证关键行为。检查预期用法以及一个
  可信的失败或恢复路径。
- 根据目标、约束和可信风险审查结果。验证是
  证据，而不是完成检查清单的回执。
- 每次失败都会成为下一步操作。修复并重复，直到所有退出条件均通过。

## 边界

- 仅在涉及保留给用户的重要决策，或不可逆的生产、
  法律/隐私、破坏性或高安全性操作时询问。
- 未经许可，绝不合并、强制推送、创建额外的 PR 或扩大终点范围。
- 在 main/master/develop 分支上编写代码前，使用
  `scripts/mux-worktree.sh <type>/<branch-name>` 创建隔离的工作树。[ETHOS：工作树隔离]
- 耗时较长或未知因素较多的工作，可以在已被 git 忽略的 `.context/implementation-notes.md` 中记录当前假设、证据、偏差和
  暂停触发条件。简短工作保留在
  对话中。

## 完成

在请求的终点停止：答复、已验证的本地改动、提交、推送、PR 或完整
交付。不要仅仅因为计划中的某个步骤完成就停止。仅当具体的验证或交付分支需要详细命令时，才查看 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/development-lifecycle/REFERENCE.md)。
