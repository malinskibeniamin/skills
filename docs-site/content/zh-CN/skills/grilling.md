盘问旨在发现影响重大的未知因素，而不是要求明确每个实现细节。在盘问期间，只要存在由用户保留决定权的重大决策，就不得编写生产代码或进行实现。调用此技能并不代表授权委派任务。

## 1. 构建证据包

阅读请求、计划、代码仓库、测试、文档、参考资料和近期决策。查明事实是智能体的职责。只有涉及偏好、范围、风险承受能力以及无法从证据中获知的决策时，才询问用户。

`/brain-dump` 是可选的前置发现步骤，并非每次盘问的必需环节。如果已有其简报，请保留每条机会方向，并从答案账本开始。将 **已确定** 项视为已有答案；除非矛盾证据使其失效，否则不要重复询问。只有当不利后果值得关注时才质疑 **暂定** 项；只有当 **未知** 项可能使某个方向失效或改变其优先级时才询问。

指出最有可能导致当前方向失效的盲点。如果观察实际行为比阅读文字说明更快得出答案，请先构建或请求一个用完即弃的原型。

## 2. 探索模式

当尚无明确方向时，提出 2 到 3 种方案，并说明权衡、可逆性和证据。推荐其中一种。相互竞争的计划交由 `/plan-arbiter` 处理。

对于面向客户的 UI 选择，请在提问环节之前放置一个 **ASCII 线框图**。在带围栏的 `text` 块中，使用可打印的 ASCII 字符勾勒每种存在实质差异的拟议布局。保持方框边框对齐，宽度适中，便于快速浏览。使用方案中的真实标签、控件、分组、顺序以及固定或滚动区域，不要使用通用占位符。将草图视为结构示意，而非像素级精确呈现；对推断出的内容加以标注。仅当布局构成在断点处发生变化时，才同时展示桌面端和移动端。如果多种方案共用同一布局，只绘制一次，并标注它们在视觉或行为上的差异。

**挑战变体：**当已有明确方向时，以最有力的方式论证最佳替代方案，并指出在什么情况下当前选择会是错误的。

绘制决策树。决策树的前沿包含当前所有可回答的决策。在一轮带编号的问题中询问整个前沿，并为每项提供建议。

使用以下固定的**问题格式**，便于用户浏览并按编号回答：

```markdown
**Q1 -- <question title>**
<question body or choices>

**Recommended:** <answer>

---

**Q2 -- <question title>**
<question body or choices>

**Recommended:** <answer>
```

尚未确定的前置条件只会延迟其所在分支，其余前沿继续推进。每轮回答后重新计算前沿。

除非用户明确授权委派，否则应在当前流程中完成事实调查。搜索环境、文件系统、工具和来源。用户的决策应由用户作出。

可采用的挑战：

- 高风险 UI 替换：回滚路径、负责人和删除条件。
- 依赖项：证明它优于本地代码，并能经受计划中的迁移。
- 抽象：展示第二个调用位置。
- 逃生舱口：下一次会话是否会复制它。
- 规模或故障断言：能够证明该断言的具体输入、时机或系统条件。

## 3. 以分类后的未知项结束

会改变架构的决策必须得到解决，或明确保留给用户决定。对其他所有事项进行分类：**查找 -> 原型 -> 可逆假设 -> 暂停触发条件**。当不存在任何可能在不被察觉的情况下导致下一个工作切片失效的未解决事项时，访谈即可结束，而不是等到所有未来细节都已明确。

## 4. 计划门禁

汇集一个**证据包**：请求、计划、规范来源、标准来源、计划路径、代码仓库事实、假设和未解决的决策。

使用与风险相匹配的最小门禁：

- **快速**：简单缺陷、任务少于三个，并且没有重大的架构、产品或 UX 选择。在当前流程中检查规范、标准和价值。
- **标准**：在当前流程中分别从产品/规范、工程/标准和设计/UX 视角进行审查。
- **深度风险**：在标准审查的基础上增加韧性审查，并以最有力的方式论证一个可信的、高影响或难以逆转的假设。

维度：规范 -> `plan-product-hat`；标准 -> `plan-engineering-hat`；设计/UX -> `plan-design-hat`；另加对抗性/价值审查。均在当前流程中执行。

深度风险触发条件：身份验证、迁移、公共 API、破坏性操作、并发、Temporal、跨服务变更和单向门决策。添加 `/resilience-review` 和 `/steelman`。

**专家注册表：**计划中的 Go 或 `go.mod` 工作使用 `/golang`；只有在反复出现遗漏后，才添加其他专家。

对于每个适用维度，报告 `APPROVED`、`NEEDS_CHANGES`、`BLOCKED` 或 `SKIPPED` 并附上证据；跳过时必须说明原因。按根本原因合并重复发现。阻塞性的用户决策会使流程暂停；事实问题则触发调查或原型构建。

仅当用户请求以计划或盘问作为终点时，才要求确认。[ETHOS: Discover Before Commitment]

使用 `/domain-modeling` 将领域术语记录到 `CONTEXT.md` 中；只有当决策难以逆转、缺少上下文时令人意外且确实存在权衡时，才编写 ADR。
