盘问旨在解决影响重大的未知因素，而不是要求明确每个细节。在盘问期间，只要存在由用户保留决定权的重大决策，就不得编写生产代码或进行实现。调用此技能并不代表授权委派任务。

## 1. 构建证据 [#1-build-evidence]

阅读请求、计划、代码仓库、测试、文档、参考资料和决策。查明事实是智能体的职责；只有涉及偏好、范围、风险承受能力以及无法从证据中获知的决策时，才询问用户。指出最有可能导致当前方向失效的盲点。如果观察实际行为比阅读文字说明更快得出答案，请构建原型。

`/brain-dump` 是可选的。保留每条机会方向，并从其**答案账本**开始：不要重复询问**已确定**项；只有当不利后果值得关注时才质疑**暂定**项；只有当**未知**项可能使某个方向失效或改变其优先级时才询问。

## 2. 探索模式 [#2-explore-mode]

当尚无明确方向时，提出 2 到 3 种方案，并说明权衡、可逆性、证据和建议。相互竞争的计划交由 `/plan-arbiter` 处理。**挑战变体：**当已有明确方向时，以最有力的方式论证最佳替代方案，并指出在什么情况下当前选择会是错误的。

对于面向客户的 UI，请在提问环节之前放置一个 **ASCII 线框图**。在带围栏的 `text` 块中，使用真实标签、控件、分组、顺序以及固定或滚动区域，勾勒每种存在实质差异的布局。保持方框边框对齐；将草图视为结构示意，而非像素级精确呈现。仅当布局构成发生变化时，才同时展示桌面端和移动端。共用的布局只需绘制一次，并标注差异。

绘制决策树，确定当前可回答的决策前沿。使用以下**问题格式**，在一轮带编号的问题中询问整个前沿：

```markdown
**Q1 -- <question title>**
<question or choices>

**Recommended:** <answer>

---

**Q2 -- <question title>**
<question or choices>
```

尚未确定的前置条件只会延迟其所在分支，其余前沿继续推进。每轮回答后重新计算前沿。除非用户明确授权委派，否则应在当前流程中完成事实调查；搜索环境、文件系统、工具和来源。用户的决策应由用户作出。

## 3. 结束 [#3-exit]

解决会改变架构的决策，或保留给用户决定。对其他事项进行分类：**查找 -> 原型 -> 可逆假设 -> 暂停触发条件**。当不存在任何可能在不被察觉的情况下导致下一个工作切片失效的未解决事项时，即可结束。

## 4. 计划门禁 [#4-plan-gate]

汇集一个**证据包**：请求、计划、规范和标准来源、计划路径、代码仓库事实、假设和未解决的决策。

- **快速**：任务少于三个，并且没有重大的架构、产品或 UX 选择；在当前流程中检查规范、标准和价值。
- **标准**：在当前流程中分别从产品/规范、工程/标准和设计/UX 视角进行审查。
- **深度风险**：在标准审查的基础上，针对一个可信的、高影响或难以逆转的假设，增加 `/resilience-review` 和 `/steelman`。

维度：规范 -> `plan-product-hat`；标准 -> `plan-engineering-hat`；设计/UX -> `plan-design-hat`；另加对抗性/价值审查。深度风险触发条件：身份验证、迁移、公共 API、破坏性操作、并发、Temporal、跨服务变更和单向门决策。

**专家注册表：**价值审查使用 `/av`；计划中的 Go 或 `go.mod` 工作使用 `/golang`；只有在反复出现遗漏后，才添加专家。每个维度报告 `APPROVED`、`NEEDS_CHANGES`、`BLOCKED` 或 `SKIPPED` 并附上证据；跳过时必须说明原因。按根本原因合并重复发现；调查事实，遇到阻塞性的用户决策时暂停。

仅当用户请求以计划或盘问作为终点时，才要求确认。[ETHOS: Discover Before Commitment]

使用 `/domain-modeling` 将术语记录到 `CONTEXT.md` 中；只有当权衡难以逆转且令人意外时，才编写 ADR。
