从固定点到 `HEAD` 生成诊断产物。除非用户明确要求发布，否则不要编辑、提交、推送、回复、解决问题或发表评论。
在主上下文中只保留一名负责人；使用智能体需要明确委派。
## 审查约定
- **目标**：确定差异是否在没有可信缺陷的情况下实现了所要求的结果。
- **约束**：仅报告由差异引入且可采取行动的发现；将已有明确记录的标准与产品/规范缺口分开；将生成的文件视为证据，而非编辑目标。
- **验证**：将主张追溯到源头。亲自通过真实入口对每项可运行的变更进行实际试用；自动化测试只是辅助证据，不能替代实际体验证据。
- **停止条件**：所有适用的表面均已纳入检查，且每项发现都有证据、后果、优先级和具体修正方案。
如果缺少固定点，请询问应以什么作为审查基准。否则，先解析当前 PR 层；对于堆叠式 PR，这会先选择其父级，再选择远程主干：
```bash
BASE=$(PR_BASE_REF="${REVIEW_BASE:-}" "${CLAUDE_PLUGIN_ROOT:-.}/scripts/resolve-pr-base.sh")
git diff "$BASE"...HEAD
git log "$BASE"..HEAD --oneline
```
## 证据循环
**检查 -> 验证 -> 分类 -> 综合。**
### 检查
1. 阅读请求或规范、仓库说明、完整差异和相关调用点。不要轻信 PR 摘要而忽略代码。
2. 对每个发生变化的假设，跨越相关的生产方、类型或模式、存储、消费方和公开表面，反向追溯到权威来源。按领域概念、数据字段和发出的值搜索，而不只是搜索发生变化的符号。
3. 使用相关未更改代码、当前基准、近期历史记录、固件或运行时输出来检验意外的主张。将差异中的注释视为假设，而非证据。
4. 将固件与生产数据形态进行比较，并构造一个行为反例，以区分预期字段或状态与其他位置可能发生的冲突。
   梳理权限和可见表面；跳过由格式化工具管理的样式问题和既有缺陷。
5. 即使测试通过且代码看似符合请求，也要思考仍可能存在什么问题。
### 验证
- 根据源代码、模式、当前主要文档或最小可执行检查来复现主张。
- 使用具有代表性的真实规模数据，执行预期路径以及一个可信的失败或恢复路径。
  亲自观察控制台、网络、日志和响应时间；测试绝不能替代实际使用。
- 如果不存在安全的可运行环境，请说明阻碍因素和所需证据；将行为保留为未验证状态，而不是推断成功。
- 检查测试完整性：公开行为、修复前正确失败、有意义的断言、覆盖率未减弱，以及不存在不稳定的时长等待。
- 针对必需行为、语义密度、领域清晰度、可信风险和已验证的规模，对每个辅助函数、分支、依赖项、选项和文件提出质疑。
优先关注跨边界矛盾，而非局部润色。
绝不要优化代码行数或鼓励代码高尔夫；应通过减少概念来保持清晰度。

仅当差异提供相关证据时，才增加针对特定表面的审查：
| 表面 | 检查项 |
|---|---|
| 面向客户的 UI/CLI/报告 | 渲染后的行为、关键状态、文案、键盘操作/无障碍性、控制台、相关视口 |
| 安全/隐私/数据丢失 | 信任边界、授权、机密信息、注入、不可逆路径和恢复路径 |
| API/模式/SQL/PostgreSQL | 兼容性、资源语义、迁移安全性、生成的输出、实际方言 |
| Go/并发/工作流 | 所有权、取消、错误、竞态、重试、幂等性 |
| 依赖项/外部 API | 当前主要文档、版本兼容性、锁文件、安全公告 |

### 分类

每项发现都必须由差异引入；影响用户或破坏约定；可复现或有具体路径支持；定位到范围最小的变更行；并附带最小且安全的修正方案和验证命令。

- **P0**：会阻止合并的暴露风险、数据丢失、服务中断、核心流程无法完成或缺失必需行为。
- **P1**：普通用户会遇到的缺陷、回归、违反约定/规范、虚假成功或严重的无障碍问题。
- **P2**：有价值、范围明确且影响较低的修正。
- **P3**：可选的未来改进或润色；默认不在行内评论中提出。

没有测量结果或结构性上限，就不要报告性能问题。没有可信风险，就不要报告边缘情况问题。
有证据支持的合理否决是有效结论。

### 综合

先列出发现。按根本原因去重，并保留有依据的最高优先级。每项发现只包含
具体路径、影响、最小修正方案和验证方式。不要复述差异或代码、赞扬作者或
叙述审查过程。重新审查时，将此前的发现标记为已修复、仍待处理或不再适用。

## 深度模式

对于 `/review --deep` 或高风险发布审计，使用相同的循环并提供完整的适用性台账。
增加结构边界、安全/依赖项工具、所有发生变化的公开表面以及精确的验证证据。阅读
[DEEP-AUDIT.md](https://github.com/malinskibeniamin/skills/blob/main/review/DEEP-AUDIT.md)；不要添加自动智能体、模型评审组或技能链。

## 输出

阅读 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/review/REFERENCE.md)，了解优先级术语和可直接用于评论的模式。
报告 `[P0|P1|P2] <file:line> <title> - <evidence, consequence, correction,
verify command>`。在发现之后附上固定点、模式、简明的实际试用记录、发现数量、
结论和剩余限制。

如果没有发现，只返回结论和剩余的验证限制。发布评论需要用户明确表达意图；
否则返回可直接用于评论的文本。
