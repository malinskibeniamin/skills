围绕一个维度审查：这项变更是否满足当前真实调用方的需求，能否证明它在用户实际运行的环境中有效，
并且能以可逆的方式落地？时间有限；快速交付、快速试错、小步迭代。
可独立运行，也可作为 **jb 审查视角**嵌入 `/review`（300 词）；代码缺陷仍由 `/review` 处理。

默认批准：这一审查视角背后的实践中，要求修改的 PR 不到 1%。
仅依据 P1 列表阻止合并，绝不因细枝末节、工作量或差异规模而阻止合并。

## 1. 选择一个类别 [#1-pick-one-lane]

阅读 PR 标题、正文、工单和差异。指定一个主要类别：

| 类别 | 值得投入时间的理由 | 预期证据 |
|---|---|---|
| `ktlo` | 维持正常运行、减少重复劳动、节省开支 | 它消除的事故、故障或开支；如有前后对比数据，也应提供 |
| `qol` | 改善 CI、开发者体验、性能、可靠性和声誉 | 谁的反馈周期缩短了，或哪个用户痛点消失了，并提供衡量结果 |
| `growth` | 客户、交易或发布需求推动的新能力；创造收入 | 当前受阻的调用方、合并后他们能做什么、准入条件、验收场景 |
| `taste` | 通过删除、统一或生成，降低下一次变更的成本 | 它删除了什么或从根本上杜绝了什么，以及为下一个使用方解除了什么阻碍 |

机械性 PR（版本升级、生成内容同步、回退、文档错别字修正）归为 `ktlo`，无需
文字说明即可认定其理由充分。为其他变更铺路的工作，应采用其所服务的面向用户变更的类别，并明确指出该变更。
一个 PR 中包含互不相关的类别时，应要求拆分。对照 RULES.md 中的**类别**判断信号。

## 2. 检验该类别的证据 [#2-test-the-lanes-evidence]

只有当 PR、工单或差异明确指出具体问题或调用方时，才标记为**理由充分**；
需要你自行推断的价值属于**证据薄弱**。**理由不成立**：没有受益方、没有问题，或只是推测性的
通用化需求。即使明确了受益方，也不能据此擅自覆盖调用方要求的内容
（模型、身份、区域、值），或偏离标准契约；这充其量也只能算证据薄弱。请问：

- `ktlo`：“如果跳过这项变更，什么会出故障、触发告警或产生费用？”
- `qol`：“谁的反馈周期会缩短，我们如何观察到这一点？”
- `growth`：“哪个调用方当前受阻，合并后他们能做什么？”
- `taste`：“这会删除什么，接下来又会降低什么的成本？”

## 3. 检查通用规则 [#3-check-cross-cutting-rules]

加载 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/jb/RULES.md) 中对应的章节；应用 S/A 级规则，仅在明确
违反 B 级规则时标记问题，C 级规则仅在摘要中提及：

- **始终检查**：范围、证据，以及批准清单和负责人决策清单。
- **上线**（功能开关、迁移、默认值、部署、公共 API、不可逆操作）：交付。
- **供使用方消费的输出**（API、UI、CLI、工具结果、错误、指标）：契约。
- **新增接口或抽象**（字段、选项、模式、服务、生成器）：设计品味。
- **开支**（模型 token、计算资源、CI 分钟数、供应商配额、重复劳动）：成本。

## 严重程度 [#severity]

- **P1**：非简单变更，却无法识别受益方或问题（`unjustified`）；
  推测性的范围：当前没有调用方需要的字段、选项、抽象、服务或模式；
  `growth` 类变更或高风险变更缺少可证伪的验收标准或验证路径；
  不可逆变更缺少功能开关、回滚方案或有记录的负责人决策。
- **P2**：类别证据为 `thin`，且存在具体后果；违反 S/A 级规则。对于默认关闭、
  需主动启用或仅用于开发的新增内容，证据缺口降为 P3。
- **P3**：B/C 级提醒、成本更低的拆分方式、后续事项；仅放在摘要中。

最多报告三个问题，优先列出影响合并决策的问题。需要上报负责人决策的事项，应明确说明不利
场景和所需决策。

## 输出 [#output]

始终以一行结论开头：

`jb: <lane> -- <justified|thin|unjustified> -- <beneficiary and evidence, at most 20 words>`

然后输出 `[P1|P2|P3] <file:line or PR body> <rule-id> -- <consequence>; <smallest fix, or the
sentence the PR body is missing>`。对于计划，请引用对应章节，并将缺失的验收
标准写成可证伪的场景。无问题通过时，仅输出结论行。
