围绕一个维度审查：这项变更是否现在就能服务于真实的调用方，能否证明它在用户实际运行的环境中有效，
并且能够可逆地落地？时间有限；快速交付，快速失败，小步迭代。
可独立运行，也可在 `/review` 中以内嵌的 **jb 评审角色**运行（300 词）；代码缺陷仍由 `/review` 处理。

默认批准。仅因 P1 列表中的问题阻止合并，绝不因细枝末节、工作量或差异大小而阻止。

## 1. 选择一个类别 [#1-pick-one-lane]

阅读 PR 标题、正文、工单和差异。指定一个主要类别：

| 类别 | 值得投入时间的理由 | 预期证据 |
|---|---|---|
| `ktlo` | 维持正常运行、消除繁琐的重复劳动、节省开支 | 它消除的事故、故障或支出；如有变更前后的数据，则提供对比 |
| `qol` | 改善 CI、开发者体验、性能、可靠性和声誉 | 用数据说明谁的工作循环缩短了，或哪项用户痛点消失了 |
| `growth` | 客户、商机或发布所需的新能力；创造收入 | 当前受阻的调用方、合并后他们能做什么、准入条件、验收场景 |
| `taste` | 通过删除、统一或生成来降低下一次变更的成本 | 它删除了什么或杜绝了什么，以及它为下一个使用方扫除了什么障碍 |

机械性 PR（版本升级、生成文件同步、回退）归为理由充分的 `ktlo`。为其他变更铺路的工作，应归入
它所服务的类别。一个 PR 中包含互不相关的类别时，应要求拆分。对照 RULES.md 中的 **Lanes** 判定信号。

## 2. 检验证据是否支撑该类别 [#2-test-the-lanes-evidence]

只有当 PR、工单或差异明确指出具体问题或调用方时，才标为**理由充分**；
需要自行推断的价值属于**证据薄弱**。**理由不成立**：没有受益方、没有问题，或只是推测性的
通用化。即使明确了受益方，也不能据此悄然覆盖调用方指定的内容
（模型、身份、区域、值），或偏离标准契约；这种情况充其量也只能算证据薄弱。请问：

- `ktlo`：“如果跳过这项工作，什么会出故障、触发告警或产生费用？”
- `qol`：“谁的工作循环会缩短，我们如何观察到这一点？”
- `growth`：“哪个调用方当前受阻，合并后他们能做什么？”
- `taste`：“这会删除什么，接下来会降低什么的成本？”

## 3. 检查通用规则 [#3-check-cross-cutting-rules]

加载 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/jb/RULES.md) 中对应的章节；执行 S/A 级规则，仅在明确
违反 B 级规则时指出，C 级规则仅在摘要中提及：

- **始终检查**：范围、证据，以及批准和负责人决策清单。
- **发布**（功能开关、迁移、默认值、部署、公共 API）：交付。
- **供使用方消费的输出**（API、UI、CLI、工具结果、错误、指标）：契约。
- **新增接口或抽象**（字段、选项、模式、服务、生成器）：品味。
- **支出**（token、计算资源、CI 分钟数、配额、繁琐的重复劳动）：成本。

## 4. 检查工程技艺 [#4-check-craft]

加载 [CRAFT.md](https://github.com/malinskibeniamin/skills/blob/main/jb/CRAFT.md)：始终检查交付和验证；涉及 Go、proto 或 SQL 时检查代码；撰写评审
评论时检查评审语气。工程技艺相关问题的严重程度最高为 P2。起草时，先将这些规则应用于草稿。

## 严重程度 [#severity]

- **P1**：非简单变更，却没有可识别的受益方或问题（`unjustified`）；
  推测性的范围：当前没有调用方需要的字段、选项、抽象、服务或模式；
  `growth` 类或高风险变更缺少可证伪的验收标准或验证路径；
  不可逆的变更，且没有功能开关、回滚方案或已记录的负责人决策。
- **P2**：类别证据为 `thin`，且存在具体后果；违反 S/A 级规则。对于默认关闭、
  需主动启用或仅用于开发的新增内容，证据缺口降为 P3。
- **P3**：B/C 级提醒、成本更低的拆分方案、后续事项；仅在摘要中提及。

最多报告三个问题，影响合并决策的问题优先。需升级给负责人处理的事项，应明确说明场景和所需决策。

## 输出 [#output]

始终以一行结论开头：

`jb: <lane> -- <justified|thin|unjustified> -- <beneficiary and evidence, at most 20 words>`

然后使用 `[P1|P2|P3] <file:line or PR body> <rule-id> -- <consequence>; <smallest fix>`。对于
计划，引用对应章节，并将缺失的验收标准写成可证伪的场景。完全通过时，只输出结论行。
