由用户调用的完整交付端点。持续工作，直到所请求的产物已交付且验证全部通过，或有证据表明确实存在外部阻塞。

## 退出约定

根据请求和仓库实时状态确定以下内容：

- **目标**：要交付的行为或变更。
- **护栏**：分支、隐私、破坏性操作以及用户保留的边界。
- **验证**：仓库检查，以及在真实入口点可观察到的行为。
- **交付**：请求所要求的提交、远程分支、PR 和 CI 状态。
- **停止条件**：所有标准均通过，或外部依赖导致无法继续推进。

## 循环

**检查 -> 验证 -> 修复 -> 重复**，直到验证通过。

1. 检查完整的分支差异和请求的端点。包括已提交、已暂存、
   未暂存和未跟踪的工作；不要交付无关文件。
2. 运行所有适用的仓库原生检查。前端工作通常包括针对性
   测试、`bun run type:check` 和 `bun run lint:fix`；Go 工作包括文档中规定的测试、
   vet 和构建检查。
3. 通过真实的用户入口点或公共入口点执行每项实质性的可运行变更。
   检查预期用法以及一种可信的故障或恢复路径。测试不能替代此步骤。
4. 对于面向客户的界面，检查渲染结果或终端结果、重要
   状态、无障碍性、控制台/错误，以及相关的视口或平台风险。
5. 根据目标、护栏、语义密度和可信风险进行一次审查。
   修复具体问题，然后使受影响的证据失效并重新运行相关验证。
6. 如果变更声称具有可衡量的影响，请重复相同的基线/候选方案场景。
   如果不存在有助于决策的衡量指标，不要虚构基准测试。

对于依赖项版本升级，请根据当前的第一方文档验证锁文件、全新安装/构建以及每个
受影响的调用点。

不要刻意制造第二次审查、清理环节、技能调用或智能体调用。由主上下文中的单一
负责人完成工作。
使用其他模型或委派通道需要用户明确授权。

## 交付

按照 [commit-push-pr/REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md) 执行明确暂存、
提交格式、推送、创建草稿 PR、审查者指引和 PR 正文相关操作。未经许可，绝不合并或
强制推送。

如果 `gh stack view --json` 识别出堆栈，请以其父层为基准审查并验证当前层。
仅当通过 `/stacked-prs` 明确提出请求时，才交付整个堆栈；普通
PR 端点不得发布其他尚未提交的层。

- 将审查和验证绑定到当前 `HEAD`；后续编辑会使这些证据失效。
- 仅因为此命令是明确的完整交付端点，才监控 CI。修复
  失败，重新执行受影响的验证，推送，然后继续。
- 解决所有现有的人工审查线程；`pr-feedback-completeness-stop` 会强制执行
  零未解决项条件。人工反馈不设上限。当前反馈全部解决后，
  不要轮询未来的反馈。
- 自我审查一旦无问题，立即停止。反复出现嘈杂的发现说明应移交处理，
  而不是随意增加轮次。
- 额外的回顾、历史记录清理或后续产物需要明确请求。

## 完成

- 已在真实入口点观察到请求的行为，或已记录无法运行的原因。
- 当前 `HEAD` 上适用的检查全部通过且无警告。
- 当前人工反馈已解决。
- 请求的提交、推送、PR 和 CI 端点已存在。
- 没有隐藏任何未提交或未跟踪的工作。
- 最终回复包含证据，并且必须以恰好一行状态信息结束。

在默认分支上，交付前请使用
`scripts/mux-worktree.sh <type>/<name>` 创建隔离的工作树。[ETHOS：工作树隔离]
