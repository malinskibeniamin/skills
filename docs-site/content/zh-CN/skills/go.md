由用户调用的完整交付端点：持续工作，直到验证通过或确实存在外部阻塞。

## 退出约定

确定目标、无法推断的护栏、仓库检查以及真实入口点行为、请求的提交/远程分支/PR/CI 交付和停止条件。

## 循环

检查 -> 验证 -> 修复 -> 重复，直到验证通过。

1. 检查完整的分支和端点：已提交、已暂存、未暂存、未跟踪。排除无关文件。
2. 运行仓库原生检查。前端工作通常包括针对性测试、`bun run type:check`、`bun run lint:fix`；Go 工作使用文档中规定的测试、vet 和构建检查。
3. 通过真实的用户入口点或公共入口点执行每项实质性的可运行变更，包括一种可信的故障或恢复路径。测试不能替代此步骤。
4. 对于面向客户的界面，检查渲染结果或终端结果、各项状态、无障碍性、错误以及相关视口/平台。对所有可见变更应用 [PR 可视化证据门禁](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md#frontendcustomer-facing-detection--screenshot-table-phase-5)。
5. 根据目标、护栏、语义密度和可信风险进行一次审查。修复问题，使受影响的证据失效并重新执行。
6. 如果变更声称具有可衡量的影响，请重复相同的基线/候选方案场景；不要虚构无用的基准测试。

对于依赖项版本升级，请根据当前的第一方文档验证锁文件、全新安装/构建以及每个受影响的调用点。

不要刻意制造审查、清理环节、技能调用或智能体调用。由主上下文中的单一负责人完成工作；使用其他模型需要用户明确授权。

## 交付

按照 [commit-push-pr/REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md) 执行暂存、提交、推送、创建草稿 PR、指定审查者和编写正文。对当前用户拥有的功能分支，可执行变基并在需要时使用 `--force-with-lease`，无需再次请求许可。未经明确许可，绝不合并、使用普通强制推送，或重写默认分支、共享分支、他人拥有或正被并行使用的分支。

如果 `gh stack view --json` 发现堆栈，请以其父层为基准验证当前层。仅当通过 `/stacked-prs` 明确提出请求时，才交付整个堆栈。

- 将证据绑定到当前 `HEAD`；后续编辑会使其失效。
- 此明确的完整交付端点会监控 CI。修复失败，重新执行验证，推送，然后继续。
- 解决所有当前的人工审查线程；`pr-feedback-completeness-stop` 会强制执行此要求。人工反馈不设上限。当前反馈全部解决后，不要继续轮询。
- 自我审查一旦无问题，立即停止。反复出现嘈杂的发现说明应移交处理，而不是随意增加轮次。
- 额外的回顾/后续产物和历史记录清理需要明确请求。

## 完成

- 已在真实入口点观察到行为，或已记录无法运行的原因。
- 当前 `HEAD` 上适用的检查全部通过且无警告。
- 当前人工反馈已解决；请求的提交/推送/PR/CI 已存在。
- 没有隐藏任何工作；最终回复包含证据，并且必须以恰好一行状态信息结束。

在默认分支上，交付前请使用 `scripts/mux-worktree.sh <type>/<name>` 创建隔离的工作树。[ETHOS：工作树隔离]
