围绕一个维度开展评审：这项变更现在是否值得发布、谁会受益，以及它是否是能够验证价值的最小
可回退切片。规则见 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ms/RULES.md)。

可针对 PR、分支、计划或工单独立运行，也可在每次 PR 评审的 `/review` 中作为 **ms 评审角色**
运行。不创建任何智能体。

## 方向 [#lanes]

每个 PR 只服务于一个方向。读取 PR 正文中的 `Lane:` 行；缺失时自行推断。

| 方向 | 何时值得投入时间 | 所需证据 |
|---|---|---|
| 维持运行 | 消除重复劳动、风险或开支 | 消除的事故、告警或成本；回退方案 |
| 改善体验 | 帮助人们摆脱阻碍或维护声誉 | 前后对比数据或问题复现；谁能感受到改善 |
| 创造新价值 | 让明确的用户群体更有可能付费或留存 | 受益者、收入路径、可发布的最小切片、默认关闭的上线方式 |
| 设计品位 | 避免代价高昂的不可逆决策，或消除一个概念 | 避免的未来成本；为什么现在做比以后做成本更低 |

涉及多个方向时应拆分，除非其中一项变更是另一项的必要前提。

## 流程 [#procedure]

1. **确定范围：** PR 标题和正文、关联工单、提交、差异。以差异为准，不轻信描述。
2. **分类：** 确定方向及涉及的领域：收入路径、客户可见功能、契约/API、运维、
   文档、CI 或开发流程、智能体平台。
3. **提问：** 现在谁会遇到这个问题，会付出什么代价？用什么可观测的证据证明已完成？
   最小的可回退切片是什么，哪些内容明确不在范围内？
4. **加载：** [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ms/RULES.md) 中对应的章节。应用 S/A 类规则、明确的 B 类违规判定，
   并仅指出显而易见的 C 类违规。
5. **评估收入可能性：** 高、中、低或无，并给出一个理由。对于维护、
   体验改善或设计品位，只要有相应证据，评为“无”也可以。未知就保持未知；
   绝不编造数字。

## 严重程度 [#severity]

- **P1：** 虚假的成功结果、健康状态或价格；将未知用量计为免费；免费用户被拒绝
  访问或受到错误限制；客户数据使用超出预期；破坏契约却没有上线方案。
- **P2：** 没有受益者或方向；混合多个方向；未经测量的性能或 CI 声称；
  推测性的通用化设计；没有可观测的完成标准；文档与行为矛盾。
- **P3：** 措辞、命名，或未声明显而易见的方向。

价值层面的发现绝不阻止已确认的正确性或安全问题修复。

## 排除项 [#exclude]

- 由其他 `/review` 评审角色负责的正确性、安全性和风格问题。
- 战略层面的否决：质疑契合度并指出缺失的证据；由负责人决定。
- 自动生成的文件。

## 输出 [#output]

`Lane: <lane> | Beneficiary: <who> | Revenue likelihood: <level> - <reason>`，然后是
`[P1|P2|P3] <rule-id> <file:line or PR body> <missing evidence> - <smallest fix>`。
该评审角色的输出限 250 词。若未发现问题：
`APPROVED -- <lane>, <beneficiary>, value evidenced.`
