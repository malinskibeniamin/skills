这是后备方案，而非生命周期步骤。整洁的代码从一开始就应保持整洁；仅当差异或代码库相较于其行为显得过于庞大时，才调用此技能。

明确提出请求时，仍可使用 Claude Code 内置的 `/simplify` 进行针对性清理。它不是生命周期门禁，也不能替代正确性审查；`/deslop` 质疑的是这些代码表面是否根本有存在的必要。

## 主张少即是多

代码是一种负债，但减少代码行数并非目标。应优先追求**语义密度**：采用最小且直观的实现，其中每个构造要么承载必需的行为，要么使领域更加清晰。优秀的代码几乎无须解释，因为它的结构与问题相契合。绝不要为了减少字符而牺牲清晰度。

按已得到证实的规模进行设计。不要为仅仅可以想象的未来添加索引、虚拟化、缓存、队列、重试、工厂、标志、配置或扩展点。

新增内容只有在表达必需行为、阐明领域或应对可信风险时，才有存在的价值。“可能发生”并非证据。

## 写入模式

仅限显式调用：`/deslop write`、"ponytail" 或 "lazy mode"。首先理解完整流程；这个阶梯缩短的是解决方案，而不是阅读过程。

1. 删除推测性范围，或保持其未实现状态。
2. 复用代码库中的现有代码。
3. 使用语言或标准库。
4. 使用平台原生能力。
5. 使用已安装的依赖项。
6. 编写最小且清晰的局部表达。
7. 只有做到以上各点后，才自行维护定制机制。

修复根本原因，而不是症状：更改共享函数前，先用 grep 检查每个调用方。在抽象能够消除真实且重复的复杂性之前，优先使用直接的代码。注释解释无法避免的原因；代码解释做了什么。

有意义的行为应保留最精简的公共契约测试。不要为琐碎的连接代码硬造测试，也不要为了缩短差异而删除有用的测试。

**强度**（`/deslop lite|full|ultra`，默认为 full）：lite 指出更省事的替代方案；full 应用上述阶梯；ultra 会质疑每一项要求，确认其合理后才保留代码。

**绝不能削减：**明确要求、信任边界验证、安全性、无障碍性，或可防止数据丢失的错误处理。

## 门禁模式

阅读目标、附近的代码、`git diff --stat` 和 `git diff`。仅标记已证实的冗余：

- `delete:` 死代码或推测性代码；直接删除，不作替代。
- `stdlib:` 用语言或标准库替代自定义代码。
- `native:` 用平台原生行为替代代码或依赖项。
- `yagni:` 没有当前需求支撑的灵活性。
- `shrink:` 以更小的表面积实现同样清晰的行为。

然后删除、内联并收紧实现。技能或测试工具的变更仍需配套的 RED -> GREEN 评估证据。运行最小范围的相关验证。

当必需行为被埋没在可避免的表面积之下时，返回 `NEEDS_CHANGES`。不要鼓励代码高尔夫，也不要移除已证实有效的安全措施。报告保留了什么、移除了什么以及原因。对于代码库审查，按合理删除规模从大到小排序；否则以 `Lean already. Ship.` 结尾。

有关精简审查清单，请参阅 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/deslop/REFERENCE.md)。
