设计**深度模块**：在清晰的接缝处，以小型接口封装大量行为，并可通过该接口进行测试。目标：为调用方提供杠杆效应，为维护者提升局部性，为智能体和人员增强可测试性。

必须立即通过增加深度来提高语义密度。不要为了假想的复用而创建模块、接缝、适配器或接口。只有当设计为调用方消除的知识和协调成本多于其引入的成本时，该设计才算成功。

## 术语表

严格使用以下术语；避免使用含义宽泛的同义词。

**模块** -- 任何由接口和实现组成的事物：函数、类、包、切片。避免使用：单元、组件、服务。

**接口** -- 调用方必须了解的一切：类型表面、不变量、顺序、错误、配置、性能。当你指的是完整契约时，避免使用 API 或签名。

**实现** -- 模块内部的内容。与**适配器**不同：适配器是填充接缝的具体事物。

**深度** -- 接口处的杠杆效应。**深** = 小型接口，大量行为。**浅** = 接口几乎与实现同样复杂。

**接缝** -- 无需编辑该处即可改变行为的位置；模块接口所在之处。避免使用“边界”，因为它承载了 DDD 限界上下文的含义。

**适配器** -- 在接缝处满足接口的具体实现；名称描述的是角色，而非实质。

**杠杆效应** -- 调用方每掌握一部分接口，便可获得更多能力。

**局部性** -- 将变更、缺陷、知识和验证集中在一处。

## 深与浅

深度模块：

```
Small Interface
----------------
Deep Implementation
```

浅层模块：

```
Large Interface
----------------
Thin Implementation
```

思考：

- 方法能否精简？
- 参数能否简化？
- 能否将更多复杂性隐藏在内部？

## 原则

- **深度是接口的属性，而非实现的大小。** 内部可以有私有接缝；调用方无需了解它们。
- **删除测试。** 如果删除一个模块会使复杂性消失，那么它只是透传层。如果复杂性重新出现在各个调用方或测试中，那么该模块便有存在的价值。
- **接口就是测试表面。** 调用方和测试跨越相同的接缝。越过接口测试内部通常意味着设计形态有误。
- **只有一个适配器意味着接缝是假想的。两个适配器意味着接缝是真实的。** 不要为想象中的变化添加接缝。
- **直接实现也是一种设计。** 小型的局部表达式优于仅仅转移代码的抽象。

## 面向可测试性进行设计

1. 接受依赖项；不要在内部创建它们。
2. 尽可能返回结果；尽量减少环境式副作用。
3. 保持表面精简：更少的方法、更少的参数、更清晰的不变量。

当两种可行的模块或接口设计都通过删除测试时，在选定其中一种之前，使用 `/plan-arbiter` 比较其深度、局部性、测试表面和回滚能力。

## 关系

- 一个模块有一个接口。
- 深度是相对于接口衡量的。
- 接缝是接口所在之处。
- 适配器位于接缝处并满足接口。
- 深度创造杠杆效应和局部性。

## 不采用的表述方式

- 用实现代码行数与接口代码行数之比衡量深度：这会奖励无意义的填充。
- 将接口仅理解为 TypeScript `interface` 或公共方法：范围过窄。
- 边界：除非指 DDD 限界上下文，否则请使用接缝或接口。
