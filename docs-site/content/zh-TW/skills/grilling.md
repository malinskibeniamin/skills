Grilling 用於解決影響重大的未知事項，而非每項細節。只要仍有保留給使用者決定的重大決策尚未定案，就不得撰寫正式環境程式碼或進行實作。呼叫此技能並不代表授權委派。

## 1. 建立證據 [#1-build-evidence]

閱讀需求、計畫、程式碼儲存庫、測試、文件、參考資料與決策。查明事實是代理程式的職責；只有偏好、範圍、風險承受度，以及無法從證據得知的決策，才詢問使用者。指出最可能使目前方向失效的盲點。如果觀察實際行為能比文字說明更快找到答案，請建立原型。

`/brain-dump` 是選用步驟。保留每個機會方向，並從其**答案登錄表**開始：不要再次詢問 **已確定** 項目；只有當不利後果值得關注時才質疑 **暫定** 項目；只有當 **未知** 項目可能使某個方向失效或改變其優先順序時才詢問。

## 2. 探索模式 [#2-explore-mode]

尚無既定方向時，提出 2 至 3 種做法，並說明取捨、可逆性、證據與建議。相互競爭的計畫交由 `/plan-arbiter` 處理。**挑戰變體：**已有既定方向時，為最佳替代方案提出最有力的論證，並指出哪些情況會證明目前選擇有誤。

對於面向客戶的 UI，請在提問前放置一份 **ASCII 線框圖**。針對每種實質不同的版面配置，在帶有 `text` 標記的程式碼圍欄中繪製草圖，使用實際標籤、控制項、分組、順序，以及固定或可捲動區域。保持方框邊界對齊；將草圖視為結構示意，而非像素級精確稿。只有當版面組成改變時，才同時顯示桌面版與行動版。共用版面只需繪製一次，並註明差異。

繪製決策樹，找出目前可回答的決策前緣。在同一個編號回合中，使用以下**問題格式**詢問整個前緣：

```markdown
**Q1 -- <question title>**
<question or choices>

**Recommended:** <answer>

---

**Q2 -- <question title>**
<question or choices>
```

尚未確定的先決條件只會延後其所屬分支，前緣其餘部分則繼續進行。每個回合後都重新計算前緣。除非使用者明確授權委派，否則應在目前流程中直接查明事實；搜尋環境、檔案系統、工具與資料來源。應由使用者作出的決策仍由使用者決定。

## 3. 結束 [#3-exit]

解決會改變架構的選擇，或保留給使用者決定。將其餘事項分類為：**查詢 -> 原型 -> 可逆假設 -> 暫停觸發條件**。在沒有任何未解決事項會悄然使下一個工作切片失效時結束。

## 4. 計畫關卡 [#4-plan-gate]

彙整一份**證據包**：需求、計畫、規格與標準來源、預計路徑、程式碼儲存庫事實、假設與未解決的決策。

- **快速**：少於三項工作，且沒有重大的架構、產品或 UX 選擇；在目前流程中直接檢查規格、標準與價值。
- **標準**：在目前流程中直接套用產品／規格、工程／標準與設計／UX 的審查觀點。
- **深度風險**：標準關卡，再加上 `/resilience-review` 與 `/steelman`，檢視可信且影響重大或難以逆轉的假設。

面向：規格 -> `plan-product-hat`；標準 -> `plan-engineering-hat`；設計／UX -> `plan-design-hat`；另加對抗性／價值觀點。深度風險觸發條件：驗證、遷移、公開 API、破壞性操作、並行處理、Temporal、跨服務工作，以及單向門決策。

**專家登錄表：**價值使用 `/av`；計畫中的 Go 或 `go.mod` 工作使用 `/golang`；只有在反覆遺漏問題後，才加入其他專家。每個面向都以證據回報 `APPROVED`、`NEEDS_CHANGES`、`BLOCKED` 或 `SKIPPED`，並說明任何略過原因。依根本原因合併重複發現；研究事實問題，並在遇到會阻擋進度的使用者決策時停止。

只有當使用者要求以計畫／grill 為終點時，才要求確認。[ETHOS: 承諾前先探索]

使用 `/domain-modeling` 將領域術語記錄於 `CONTEXT.md`；只有當取捨難以逆轉，且缺少背景時會令人意外，才建立 ADR。
