Grilling 用於找出影響重大的未知事項；它不要求每項實作細節都確定無疑。在 grilling 期間，只要仍有保留給使用者決定的重大決策尚未定案，就不得撰寫正式環境程式碼或進行實作。呼叫此技能並不代表授權委派。

## 1. 建立證據包

閱讀需求、計畫、程式碼儲存庫、測試、文件、參考資料與近期決策。查明事實是代理程式的職責。只有偏好、範圍、風險承受度，以及無法從證據得知的決策，才詢問使用者。

指出最可能使目前方向失效的盲點。如果觀察實際行為能比文字說明更快找到答案，請先建立或要求提供可拋棄式原型。

## 2. 探索模式

尚無既定方向時，提出 2 至 3 種做法，並說明取捨、可逆性與證據。推薦其中一種。相互競爭的計畫交由 `/plan-arbiter` 處理。

對於面向客戶的 UI 選擇，請在提問回合前放置一份 **ASCII 線框圖**。針對每種實質不同的版面配置提案，使用可列印的 ASCII 字元，在帶有 `text` 標記的程式碼圍欄中繪製草圖。保持方框邊界對齊，寬度也應足以快速瀏覽。請使用提案中的實際標籤、控制項、分組、順序，以及固定或可捲動區域，而非通用預留位置。將草圖視為結構示意，而非像素級精確稿；推斷的內容應加以標示。只有當版面組成會在中斷點改變時，才同時顯示桌面版與行動版。若多種做法共用同一版面，只需繪製一次，並註明其視覺或行為差異。

**挑戰變體：**已有既定方向時，為最佳替代方案提出最有力的論證，並指出哪些情況會證明目前選擇有誤。

繪製決策樹。其前緣包含目前所有可回答的決策。在同一個編號回合中詢問整個前緣，並為每項問題提供建議。

使用以下固定的**問題格式**，讓使用者能快速瀏覽並依編號回答：

```markdown
**Q1 -- <question title>**
<question body or choices>

**Recommended:** <answer>
```

尚未確定的先決條件只會延後其所屬分支，前緣其餘部分則繼續進行。每個回答回合後都重新計算前緣。

除非使用者明確授權委派，否則應在目前流程中直接查明事實。搜尋環境、檔案系統、工具與資料來源。應由使用者作出的決策仍由使用者決定。

實用的挑戰問題：

- 高風險 UI 替換：復原路徑、負責人與刪除條件。
- 相依套件：證明其優於本機程式碼，且能在計畫中的遷移後繼續使用的證據。
- 抽象化：已證實存在第二個呼叫位置。
- 逃生機制：下一個工作階段是否會複製這種做法。
- 規模或失敗主張：能證明該主張的具體輸入、時機或系統條件。

## 3. 以分類後的未知事項結束

會改變架構的決策必須解決，或明確保留給使用者決定。將其他所有事項分類為：**查詢 -> 原型 -> 可逆假設 -> 暫停觸發條件**。訪談應在沒有任何未解決事項會悄然使下一個工作切片失效時結束，而不是等到所有未來細節都已知才結束。

## 4. 計畫關卡

彙整一份**證據包**：需求、計畫、規格來源、標準來源、預計路徑、程式碼儲存庫事實、假設與未解決的決策。

使用符合風險的最小關卡：

- **快速**：小問題、少於三項工作，且沒有重大的架構、產品或 UX 選擇。在目前流程中直接檢查規格、標準與價值。
- **標準**：在目前流程中直接套用產品／規格、工程／標準與設計／UX 的觀點。
- **深度風險**：標準關卡，再加上韌性檢視，以及針對可信、影響重大或難以逆轉之假設的最有力反方論證。

面向：規格 -> `plan-product-hat`；標準 -> `plan-engineering-hat`；設計／UX -> `plan-design-hat`；另加對抗性／價值觀點。直接在目前流程中執行。

深度風險觸發條件：驗證、遷移、公開 API、破壞性操作、並行處理、Temporal、跨服務變更，以及單向門決策。加入 `/resilience-review` 與 `/steelman`。

**專家登錄表：**計畫中的 Go 或 `go.mod` 工作使用 `/golang`；只有在反覆遺漏問題後，才加入其他專家。

針對每個適用面向，以證據回報 `APPROVED`、`NEEDS_CHANGES`、`BLOCKED` 或 `SKIPPED`；略過時必須說明原因。依根本原因合併重複發現。會阻擋進度的使用者決策應使流程停止；事實問題則應觸發研究或原型製作。

只有當使用者要求以計畫／grill 為終點時，才要求確認。[ETHOS: 承諾前先探索]

使用 `/domain-modeling` 將領域術語記錄於 `CONTEXT.md`；只有當決策難以逆轉、缺少背景時會令人意外，且確實存在取捨時，才建立 ADR。
