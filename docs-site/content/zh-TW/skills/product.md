[開啟可編輯的 Excalidraw 原始檔](/diagrams/skills/product.excalidraw)

每個計畫、PR 和審查都要回答一個問題：這項變更是否值得投入時間，
而且能否觸及它要服務的人？只評估價值：程式碼缺陷交由 `/review` 處理，主張
與證據的比對交由 `/lie-detector` 處理。可獨立執行，也可在
`/review` 和 `/grilling` 中以**產品視角**介入，並用於自動審查流程。[RULES.md](https://github.com/malinskibeniamin/skills/blob/main/product/RULES.md) 依據
有多少組獨立證據得出一致結論，為每條規則評級；[CRAFT.md](https://github.com/malinskibeniamin/skills/blob/main/product/CRAFT.md) 則是
作者用來選擇、塑造、測試及交付工作的實務指南。

## 類別 [#lanes]

每項變更都應服務一個主要類別。混合目的應拆成不同的 PR。

| 類別 | 如何讓投入的時間值得 | 有效證據 |
| --- | --- | --- |
| 維持運作 | 節省成本或避免損失：故障、閒置成本、繁瑣作業、無人使用的功能介面、計費與升級流程 | 事故或重現步驟、金額、繁瑣作業工時、已驗證的修正 |
| 改善日常體驗 | 提升速度與信譽：CI 與開發迭代流程、延遲、可據以採取行動的錯誤訊息、可實際執行的文件、偶發失敗 | 變更前後的數據、誰因此解除阻礙、發生頻率 |
| 功能 | 創造營收：明確的買家、客群、上市活動或展示情境能做到新的事 | 明確的需求、可觸及的介面、採用訊號 |
| 設計品味 | 降低下一次變更的成本：單一事實來源、標準化路徑、類別防護、刪除 | 已造成的偏離或維護成本、第二個呼叫端 |

## 模式 [#modes]

| 模式 | 使用時機 | 輸出 |
| --- | --- | --- |
| 規劃 | 撰寫程式碼前的議題、規格或計畫；`/grilling` 的產品視角 | 判定、Given/When/Then 驗收條件、成本最低的反證方式、切片計畫 |
| 撰寫 | 撰寫 PR，包括 `/commit-push-pr` | `Lane:` 行，以及能回答審查者疑問的內文（[CRAFT.md](https://github.com/malinskibeniamin/skills/blob/main/product/CRAFT.md)） |
| 審查 | `/review`、自動審查流程、明確要求 | 一行判定與最多三項發現 |
| 追蹤 | 長期分支、堆疊式 PR，或範圍持續擴大的工作 | `on track`、`drifting` 或 `park`，以及應刪減的範圍 |

## 程序 [#procedure]

1. **意圖：**閱讀計畫或 PR 內文、連結的議題、提交紀錄及完整差異；絕不因為
   摘要而忽略程式碼。記錄宣告的類別（`Lane:` 行），或推斷類別並明確註明。
2. **受益者：**指出角色，以及這項變更會為他們帶來什麼改變。只寫「使用者」或「清理」
   並不算指出受益者。
3. **為何現在做：**找出觸發原因（事故、客戶要求、上市、交易、成本激增、
   實測退步、使用方受阻）。若沒有，這項工作就必須與路線圖上的項目競爭資源。
4. **證據：**實測 > 重現 > 明確指出 > 單純宣稱。效能、成本與
   可靠性的主張需要數據；假設若遭推翻，就結束這項工作。
5. **觸及：**追蹤價值是否能透過受益者目前使用的介面送達：UI、API、CLI、文件，
   或已在某處啟用的功能旗標。已合併但無法觸及的變更，尚未產生價值。
6. **持有成本：**將執行成本、新增介面、相依套件、待命負擔及審查時間，
   與最簡單的替代方案比較。
7. **切片與安全性：**採用最小且可獨立產生價值的切片，預設關閉並提供回復方式，
   保護現有使用方，將不可逆決策留給負責人。
8. **規則：**一律套用 RULES.md 的正當理由、範圍與證據章節，以及
   所屬類別的章節；若差異涉及推出、客戶可見的輸出或
   計費，則套用交付、信任或金錢章節。強制執行 S 與 A；差異明確符合時套用 B；只有在要求時才套用 C。

追蹤模式會將分支與其宣告的成果比較：超出類別範圍的工作屬於
`drifting`（指出應刪減的內容或後續 PR）；尚無法交付的價值則標為 `park`
（指出重新啟動的條件）。

## 判定與嚴重程度 [#verdicts-and-severity]

- **justified**：每個步驟都有證據支持。直接核准，不多加評論。
- **thin**：確實有價值，但缺少證據、驗收條件、觸及方式或推出安排；完成
  指定修正後即可交付。
- **unjustified**：沒有受益者或觸發原因、介面需求僅憑臆測，或成本高於回報；
  重新思考範圍，或暫擱並訂定重新啟動的條件。

- **P1 Value**：誤報成功或無聲地未執行任何動作；漏收或重複收費；正式環境路徑中斷
  且無法關閉；未經負責人同意就做出不可逆決策；不實的公開主張。
- **P2 Value**：缺少受益者、觸發原因、證據、驗收條件或推出安排；介面需求僅憑
  臆測；混合多種類別。
- **P3**：提醒建議；自動化流程絕不發布此類意見。

絕不單憑設計品味阻擋變更。評級決定規則適用的強度；嚴重程度只能依據
這份清單判定。

## 自動審查 [#automated-review]

保持安靜表示價值理由清楚：判定為 **justified** 的變更只會收到一行判定。
否則，發布一則最上層的 Value 留言，包含最多三項 P1 或 P2 發現，每項都須列出
規則 ID、後果與最小修正。絕不重述 PR 內容。僅涉及價值的發現
只留下留言，絕不要求變更；由負責人決定。依據內容本身的價值評估機器人的發現。

## 輸出 [#output]

```
product: <ktlo|qol|feature|taste> (<declared|inferred>) -- <justified|thin|unjustified> -- <beneficiary>; trigger: <why now>; evidence: <strongest proof>
- [P1|P2 Value] <rule id> <gap> - <consequence> - <smallest fix>
```

規劃模式會加上驗收情境與成本最低的反證方式。追蹤模式則在判定欄位填入
`on track`、`drifting` 或 `park`。
