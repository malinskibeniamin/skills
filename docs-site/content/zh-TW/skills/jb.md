[開啟可編輯的 Excalidraw 原始檔](/diagrams/skills/jb.excalidraw)


聚焦一個面向進行審查：這項變更是否現在就能服務實際的呼叫端、證明它在使用者的執行環境中有效，
且能以可逆的方式交付？時間有限；快速交付、快速試錯，以小幅變更持續迭代。
可獨立執行，也可在 `/review` 中以 **jb 審查角色**執行（300 字）；程式碼缺陷仍由 `/review` 處理。

預設核准。只有 P1 清單中的問題才能阻擋，不因瑣碎問題、所需工時或差異大小而阻擋。

## 1. 選擇一個類別 [#1-pick-one-lane]

閱讀 PR 標題、內文、工單與差異。指定一個主要類別：

| 類別 | 值得投入時間的原因 | 預期證據 |
|---|---|---|
| `ktlo` | 維持運作、消除繁瑣作業、節省成本 | 能排除的事件、故障或支出；若有前後比較數據，則附上 |
| `qol` | 改善 CI、開發者體驗、效能、可靠性與聲譽 | 縮短了誰的作業週期，或消除了哪項使用者痛點，並提供量測結果 |
| `growth` | 由客戶、交易或產品推出需求驅動的新能力；創造收入 | 目前受阻的呼叫端、合併後能做什麼、通過條件、驗收情境 |
| `taste` | 透過刪除、統一或產生內容，降低下次變更的成本 | 刪除了什麼或杜絕了什麼，以及為下一個使用端排除了什麼阻礙 |

機械式 PR（版本更新、產生檔案同步、還原變更）歸為有充分依據的 `ktlo`。前置工作應歸入
其所支援的類別。同一個 PR 若包含互不相關的類別，應要求拆分。對照 RULES.md 的 **Lanes** 判斷依據。

## 2. 檢驗該類別的證據 [#2-test-the-lanes-evidence]

只有當 PR、工單或差異明確指出具體問題或呼叫端時，才標記為**有充分依據**；
若價值必須自行推斷，則屬於**依據薄弱**。**缺乏依據**：沒有受益者、沒有問題，或僅為推測性的
通用需求。即使指明受益者，也不能合理化未告知就覆寫呼叫端的要求
（模型、身分、區域、值），或偏離標準契約；這頂多只能算依據薄弱。請問：

- `ktlo`：「如果略過這項工作，什麼會故障、觸發值班告警，或產生費用？」
- `qol`：「誰的作業週期會縮短？我們要如何觀察？」
- `growth`：「目前哪個呼叫端受阻？合併後他們能做什麼？」
- `taste`：「這會刪除什麼？接下來哪項工作的成本會降低？」

## 3. 檢查跨類別規則 [#3-check-cross-cutting-rules]

載入 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/jb/RULES.md) 中對應的章節；套用 S/A，只有明確
違反 B 時才標示，C 則僅在摘要中提及：

- **一律檢查**：Scope、Evidence，以及核准與負責人決策清單。
- **推出**（功能旗標、遷移、預設值、部署、公開 API）：Delivery。
- **供使用端取用的輸出**（API、UI、CLI、工具結果、錯誤、指標）：Contracts。
- **新增介面或抽象概念**（欄位、選項、模式、服務、產生器）：Taste。
- **支出**（token、運算資源、CI 分鐘數、配額、繁瑣作業）：Cost。

## 4. 檢查實作品質 [#4-check-craft]

載入 [CRAFT.md](https://github.com/malinskibeniamin/skills/blob/main/jb/CRAFT.md)：一律檢查 Ship 與 Verify；涉及 Go、proto 或 SQL 時檢查 Code；撰寫
評論時檢查 Review voice。實作品質的發現最高列為 P2。撰寫時，先將這些規則套用到草稿。

## 嚴重程度 [#severity]

- **P1**：非瑣碎變更卻沒有可辨識的受益者或問題（`unjustified`）；
  推測性的範圍：目前沒有呼叫端需要的欄位、選項、抽象概念、服務或模式；
  `growth` 或高風險變更缺乏可證偽的驗收條件或驗證途徑；
  不可逆的變更卻沒有功能旗標、回復機制，或已記錄的負責人決策。
- **P2**：類別證據為 `thin`，且有具體後果；違反 S/A 規則。預設關閉、
  需主動啟用或僅供開發使用的新增項目，其證據缺口降為 P3。
- **P3**：B/C 提醒、成本更低的拆分方式、後續工作；僅列於摘要。

最多回報三項發現，影響合併決策的項目優先。需上呈負責人的事項，應指明情境與需要做出的決策。

## 輸出 [#output]

一律以一行判定開頭：

`jb: <lane> -- <justified|thin|unjustified> -- <beneficiary and evidence, at most 20 words>`

接著輸出 `[P1|P2|P3] <file:line or PR body> <rule-id> -- <consequence>; <smallest fix>`。對於
計畫，請引用章節，並將缺少的條件寫成可證偽的情境。若審查通過且沒有問題，只輸出判定行。
