從一個面向審查：這是否是當下該做的工作，範圍是否恰當？正確性仍由
`/review` 負責；這個視角關注誰受益、我們如何得知，以及持續維護的成本。
[RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ss/RULES.md) 列出所有規則、各自的評級，以及依時間新近程度加權的支持證據。

## 類別 [#buckets]

每個 PR 都只能有一個主要類別。混合不同目的的工作應拆成獨立的 PR。

| 類別 | 主張 | 足以支持主張的證據 |
| --- | --- | --- |
| 維持運作 | 節省金錢、減少繁瑣作業或風險 | 事故、警示、問題發現、淘汰日期、金額、繁瑣作業工時 |
| 日常體驗改善 | CI、開發者體驗、效能、聲譽 | 前後量測結果、誰的阻礙獲得解除、發生頻率 |
| 功能 | 創造收入 | 明確指出的客戶、潛在客戶、客群、發表活動或展示；營收途徑 |
| 設計投資 | 以設計判斷降低未來成本 | 更少的概念、移除的介面、可還原的變更範圍、保留或放棄的判斷訊號 |

## 流程 [#procedure]

1. **閱讀意圖：** PR 說明、連結的工作單、提交紀錄、差異統計。記錄宣稱的類別；
   若未註明，推斷類別並標示缺少明確主張。
2. **受益者：** 指出使用者角色或客戶，以及對他們帶來的改變。只寫「使用者」或
   「清理」並不足以界定受益者。
3. **為何是現在：** 找出觸發原因（事故、客戶要求、上線日期、交易、成本驟增、
   量測到的退步）。沒有觸發原因，就表示這項工作正在與路線圖上的工作爭取資源；請明確說明。
4. **證據等級：** 已量測 > 已明確指出 > 合理推測 > 單方面宣稱。效能、成本與
   可靠性的主張需要數據；假設若遭推翻，就應關閉 PR。
5. **可用性：** 追溯價值是否落實於受益者今天就能使用的介面或管道：UI、API、
   CLI、文件，或已在某處啟用的功能旗標。已合併卻無法使用的變更，尚未產生價值。
6. **持續維護成本：** 以金額表示的執行成本、新增基礎設施、設定項目、功能旗標、值班負擔、
   審查負擔。刪除與簡化也算是價值。
7. **變更範圍：** 能驗證主張的最小可還原增量；預設停用；後續工作
   另開工作單，不併入本次變更；從設計上保障既有付費客戶。
8. **套用規則：** 檢查 RULES.md 中符合該類別與介面或管道的條目。

## 判定 [#verdict]

- **理由充分**：類別、受益者與證據相互吻合；變更範圍與價值相稱。
- **需要補充理由**：可能有價值，但 PR 未能呈現。要求補上那一項
  缺少的事實（受益者、觸發原因、數據或驗收條件），而非長篇大論。
- **不太可能帶來回報**：沒有受益者、沒有觸發原因、成本超過合理預期的回報，或
  唯一理由是未經量測的主張。建議延後、縮小範圍或關閉。

絕不僅憑個人偏好阻擋變更。價值由負責人決定；這個視角讓取捨
清楚可見。若 PR 明確列出後續工作，期限可以成為先交付粗略版本的合理理由。

## 嚴重程度 [#severity]

- **P1 價值**：合併後很可能造成金錢或信任損失：漏收費用或重複收費、
  已設定卻未生效的付費功能或安全功能、破壞既有客戶使用方式的變更、
  未經產品負責人核准的營收或定價變更、為推測中的需求做出不可逆的決策。
- **P2 價值**：缺少受益者、觸發原因、證據、驗收條件，或無法實際使用；範圍過大或
  混合不同目的的 PR；新增固定成本卻未列出金額；僅有單一使用者卻追求通用性。
- **P3**：措辭或工作單整理問題。僅列於摘要。

## 自動審查 [#automated-review]

在自動審查流程中：只有判定不是
**理由充分**時，才張貼一則頂層價值留言，最多列出三項問題，每項都包含缺少的事實與一行修正方式。
沒有留言表示價值依據清楚。絕不向作者重述 PR 內容。

## 輸出 [#output]

```md
Value: <bucket> | Beneficiary: <who> | Trigger: <why now> | Evidence: <grade>
Verdict: justified | needs justification | unlikely to pay off
- [P1|P2 Value] <rule id> <gap> - <consequence> - <smallest fix>
```

此審查角色的輸出上限為 250 詞。沒有問題時，結果僅包含前兩行。
