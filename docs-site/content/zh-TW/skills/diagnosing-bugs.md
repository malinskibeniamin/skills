針對疑難錯誤的嚴謹方法。只有在說明理由時才能略過階段。使用領域詞彙表與 ADR；
若涉及第三方/API/版本漂移，請先執行 `/read-the-damn-docs`，再排列假設的優先順序。

## 遮蔽敏感資訊
此技能會顯示命令、輸出與擷取的成品。**先遮蔽所有密鑰** --
以 `<REDACTED>` 取代。使用環境變數建立迴圈，避免憑證進入檔案與引用的輸出。
擷取的成品可能包含驗證標頭；只引用帶有有效訊號的行。若遮蔽後的證據不足，
請向使用者要求更安全的來源。

## 階段 1 -- 建立回饋迴圈
**回饋迴圈就是這項技能的核心。**其餘都是機械式作業。為回報的錯誤建立快速、確定性、
可由代理程式執行的通過/失敗訊號；二分搜尋、假設測試與
檢測工具都會使用該訊號。將大部分診斷心力投入此處。

### 策略（大致依此順序嘗試）
1. 在能觸及錯誤的最高層接縫建立**失敗測試** -- 單元、整合或端對端測試。
2. 對執行中的開發伺服器使用 **Curl / HTTP 指令稿**。
3. 使用固定輸入進行 **CLI 呼叫**，比較標準輸出與已知正確的快照。
4. **無頭瀏覽器指令稿**（Playwright / Puppeteer）-- 操作 UI，驗證 DOM/主控台/網路。
5. **重播擷取的追蹤記錄。**將真實的網路請求 / 承載資料 / 事件記錄儲存至磁碟；透過隔離的程式碼路徑重播。
6. **拋棄式測試工具。**啟動能以一次呼叫觸及錯誤的最小系統切片。
7. **屬性 / 模糊測試迴圈。**如果錯誤是「輸出有時不正確」，請執行 1000 組隨機輸入並觀察失敗模式。
8. **二分搜尋測試工具。**如果錯誤出現在兩個已知狀態之間，請將
   「啟動狀態 X、檢查、重複」自動化，使 `git bisect run` 能夠運作。
9. **差異比較迴圈。**讓相同輸入通過舊版本與新版本（或兩種設定），再比較輸出差異。
10. **HITL Bash 指令稿。**最後手段。如果必須由人工點擊，請使用
    `scripts/hitl-loop.template.sh` 引導操作；將擷取的輸出送回迴圈。

### 反覆改善迴圈本身
將迴圈視為產品：提高速度、精確鎖定要驗證的症狀，並透過固定時間、隨機種子、
檔案系統狀態與網路輸入來消除不確定性。

### 非確定性錯誤
以**提高重現率**為目標。重複執行迴圈、加入受控壓力，並
縮小時序窗口，直到失敗發生得足夠頻繁，能夠區分各項假設。

### 確實無法建立迴圈時
停止作業，列出已嘗試的迴圈，並要求缺少的輸入：可存取能重現問題的
環境、已擷取的成品，或進行暫時性正式環境檢測的權限。

當迴圈能可靠地顯示回報的失敗時，進入階段 2。

## 階段 2 -- 重現
執行迴圈，接著使用 `/dogfood` 測試回報者實際使用的進入點。確認同一個錯誤出現。

- [ ] 迴圈產生的是**使用者**所描述的失敗模式，而非相近的其他失敗。
- [ ] 失敗能在多次執行中重現，或發生頻率足以進行偵錯。
- [ ] 迴圈擷取了確切症狀，讓階段 5 能證明修正確實解決該問題。

當回報的錯誤能夠重現時繼續。

## 階段 3 -- 提出假設
在測試前先提出 **3-5 個依優先順序排列且可證偽的假設**；只採用單一假設會
使工作錨定在第一個看似合理的想法上。

> 格式：「如果 <X> 是原因，那麼 <改變 Y> 將使錯誤消失 / <改變 Z> 將使錯誤惡化。」

捨棄或改進任何缺乏可測試預測的假設。

在測試前顯示依優先順序排列的清單，讓現有的領域知識能重新排序。使用者不在場時，
依據證據排列的順序繼續進行。

## 階段 4 -- 加入檢測
每項探測都必須對應階段 3 的特定預測。**一次只改變一個變數。**

1. 環境支援時使用**偵錯工具 / REPL 檢查**。一個中斷點即可取代十筆記錄。
2. 在能區分各項假設的邊界加入**針對性記錄**。
3. 絕不「記錄所有內容再用 grep 搜尋」。

以唯一前綴標記每筆偵錯記錄，例如 `[DEBUG-a4f2]`，然後移除所有相符項目。

**效能分支。**使用計時測試工具、分析器或查詢計畫建立實測基準，
再進行二分搜尋。先測量，再修正。

## 階段 5 -- 修正 + 迴歸測試

在修正前先撰寫迴歸測試 -- 但僅限於有**正確接縫**可供測試時。

正確的接縫會依照呼叫端實際發生的方式，觸發**真實的錯誤模式**。無法重現觸發鏈的淺層
單元測試會帶來虛假的信心。如果沒有合適的接縫，請為階段 6 記錄這項架構缺口。否則：

1. 將最小化重現案例轉換成該接縫的失敗測試。
2. 確認測試失敗。
3. 套用修正。
4. 確認測試通過。
5. 執行 `/dogfood` 以重播完全相同的使用者重現流程，再重新執行階段 1 原始且未最小化的迴圈。

## 階段 6 -- 清理 + 事後檢討
在宣布診斷完成前，完成每一項：

- [ ] `/dogfood` 確認完全相同的使用者重現流程不再重現問題；階段 1 的迴圈也通過
- [ ] 迴歸測試通過（或已記錄缺少接縫）
- [ ] 已移除所有 `[DEBUG-...]` 檢測程式碼（使用 `grep` 搜尋前綴）
- [ ] 已刪除拋棄式原型（或移至明確標示的偵錯位置）
- [ ] 在提交 / PR 訊息中陳述最終證實正確的假設 -- 讓下一位偵錯人員能從中學習

接著詢問如何避免問題再次發生。如果答案是架構變更，請將
具體的接縫或耦合問題交給 `/improve-codebase-architecture`。在根本原因
修正後、證據最充分時提出建議。
