設計**深層模組**：在清楚的接縫上，以小型介面封裝大量行為，並可透過該介面進行測試。目標：為呼叫端提供槓桿效益、為維護者提升局部性，並讓代理程式與人員都能輕鬆測試。

深度現在就必須提高語意密度。不要為了假想的重複使用情境建立模組、接縫、轉接器或介面。唯有當設計為呼叫端移除的知識與協調成本，多於它所引入的成本時，這項設計才算成功。

## 詞彙表

請精確使用下列術語，避免使用含義寬鬆的同義詞。

**模組** -- 任何包含介面與實作的事物：函式、類別、套件、切片。避免使用：單元、元件、服務。

**介面** -- 呼叫端必須知道的一切：型別表面、不變條件、順序、錯誤、設定、效能。若指的是完整契約，避免使用 API 或簽章。

**實作** -- 模組內部的內容。不同於**轉接器**：轉接器是在接縫處提供實作的具體事物。

**深度** -- 介面所提供的槓桿效益。**深層** = 小型介面、大量行為。**淺層** = 介面幾乎與實作同樣複雜。

**接縫** -- 無須編輯該處即可改變行為的位置；也是模組介面所在之處。避免使用「邊界」，因為此詞與 DDD 的限界上下文概念重疊。

**轉接器** -- 在接縫處滿足介面的具體實作；名稱描述的是角色，而非實質內容。

**槓桿效益** -- 呼叫端每學習一項介面，就能獲得更多能力。

**局部性** -- 讓變更、錯誤、知識與驗證集中在一處。

## 深層與淺層

深層模組：

```
Small Interface
----------------
Deep Implementation
```

淺層模組：

```
Large Interface
----------------
Thin Implementation
```

請思考：

- 方法能否縮減？
- 參數能否簡化？
- 能否在內部隱藏更多複雜性？

## 原則

- **深度是介面的屬性，而非實作的大小。** 內部可以有私有接縫；呼叫端無須了解它們。
- **刪除測試。** 如果刪除模組會讓複雜性一併消失，那它只是直通層。如果複雜性重新出現在各個呼叫端或測試中，則該模組確實有其價值。
- **介面就是測試表面。** 呼叫端與測試會跨越相同的接縫。越過介面測試內部，通常表示模組形狀不正確。
- **一個轉接器代表假想的接縫；兩個轉接器代表真實的接縫。** 不要為想像中的變化加入接縫。
- **直接作法本身就是一種設計。** 簡短的區域運算式，勝過只是搬移程式碼的抽象層。

## 為可測試性而設計

1. 接受相依項目；不要在內部建立它們。
2. 盡可能回傳結果；將環境中的副作用降至最低。
3. 保持表面精簡：更少的方法、更少的參數、更清楚的不變條件。

當兩種可行的模組／介面設計都通過刪除測試時，請先使用 `/plan-arbiter` 比較深度、局部性、測試表面與回復能力，再決定採用其中一種。

## 關係

- 一個模組具有一個介面。
- 深度是相對於介面衡量的。
- 接縫是介面所在之處。
- 轉接器位於接縫處並滿足介面。
- 深度會產生槓桿效益與局部性。

## 不採用的詮釋方式

- 將深度視為實作行數／介面行數：這會鼓勵灌水。
- 將介面僅視為 TypeScript `interface` 或公用方法：範圍過於狹窄。
- 邊界：除非指的是 DDD 限界上下文，否則請使用接縫或介面。
