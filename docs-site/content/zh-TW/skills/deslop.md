這是備援措施，不是生命週期。乾淨的程式碼一開始就應該是乾淨的；只有
當差異或儲存庫相較於其行為顯得過度龐大時，才應叫用此技能。

若明確提出要求，Claude Code 內建的 `/simplify` 仍可用於
戰術性清理。它不是生命週期關卡，也不能取代正確性審查；
`/deslop` 質疑的是這些表層內容是否根本有存在的必要。

## 主張少即是多

程式碼是負債，但負 LOC 並非目標。應優先追求**語意密度**：
在最精簡且一目了然的實作中，每個結構都承載必要行為
或闡明領域概念。優美的程式碼幾乎不需要
解釋，因為其形式與問題相符。絕不可為了減少字元而犧牲清晰度。

針對已證實的規模進行設計。不要為了純屬想像的未來而加入索引、
虛擬化、快取、佇列、重試、工廠、旗標、設定或擴充點。

新增內容必須能表達必要行為、闡明領域概念或處理可信風險，才值得保留。「可能發生」並不是證據。

## 寫入模式

僅限明確要求：`/deslop write`、"ponytail" 或 "lazy mode"。先完整理解
整個流程；階梯縮短的是解決方案，絕不是閱讀範圍。

1. 刪除推測性範圍，或保留為尚未建置。
2. 重複使用程式碼庫中的現有內容。
3. 使用語言本身或標準函式庫。
4. 使用原生平台功能。
5. 使用已安裝的相依套件。
6. 撰寫最精簡且清晰的區域性表達方式。
7. 只有到這一步，才自行維護自訂機制。

修正根本原因，而非症狀：變更共用
函式前，先用 grep 找出每個呼叫端。在抽象化確實能消除重複的
複雜度之前，優先採用直接的程式碼。註解說明無可避免的原因；程式碼說明做了什麼。

有意義的行為應保留最精簡的公開契約測試。不要為瑣碎的串接程式碼
硬造測試，也不要為了縮短差異而刪除有用的測試。

**強度**（`/deslop lite|full|ultra`，預設為 full）：lite 指出更省力的
替代方案；full 套用此階梯；ultra 在保留程式碼前，會質疑每一項需求。

**絕不可刪減：**明確需求、信任邊界驗證、安全性、
無障礙功能，或能防止資料遺失的錯誤處理。

## 關卡模式

閱讀目標、鄰近程式碼、`git diff --stat` 和 `git diff`。僅標記已證實的
多餘內容：

- `delete:` 無作用或推測性的程式碼；直接刪除，不需取代。
- `stdlib:` 以語言本身或標準函式庫取代自訂程式碼。
- `native:` 以平台行為取代程式碼或相依套件。
- `yagni:` 沒有當前需求的彈性設計。
- `shrink:` 以更小的表層範圍提供同樣清晰的行為。

接著刪除、內嵌並收緊實作。技能或測試框架的變更仍需有相符的
RED -> GREEN 評估證據。執行範圍最小且相關的驗證。

當必要行為埋沒在可避免的表層內容下時，回傳 `NEEDS_CHANGES`。
不要鼓勵程式碼高爾夫，也不要移除已證實有效的安全措施。回報哪些內容保留、
哪些內容移除，以及原因。進行儲存庫稽核時，依合理刪除量由大到小排列；
否則以 `Lean already. Ship.` 作結。

如需精簡的審查檢查清單，請參閱 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/deslop/REFERENCE.md)。
