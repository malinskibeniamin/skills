負責一項成果並持續推進，直到有證據證明成果已達成，或出現真正的阻礙。

## 成果契約

編輯前，從請求與儲存庫中擷取四項內容：

- **目標**：高階的最終狀態。
- **護欄**：無法推斷的儲存庫限制、保留給使用者決定的事項，以及
  不可逆的界線。
- **驗證**：可執行的檢查或可觀察的行為，用以區分確實完成與
  看似可行。
- **停止條件**：要求的終點，以及確實需要使用者介入的情況。

不要將其擴展為預測的程式碼或冗長程序。範圍明確的建置、修正或
實作請求即代表已授權執行：簡要陳述契約後立即繼續。

## 執行迴圈

**檢查 -> 行動 -> 驗證 -> 重複。**

### 檢查

- 找出最可能使做法失效的盲點。
- 閱讀程式碼、測試、記錄、目前的文件與鄰近範例。比起另一份文字摘要，
  優先採用可執行的證據。
- 優先釐清變動性最高的未知事項。將其餘事項分類為查詢、原型、
  可逆假設或暫停觸發條件。
- 遵循現有慣例與已展現的規模。只有在觀察到的任務進入特定領域時，
  才載入專業指引。

### 行動

- 由一個主要模型擔任唯一負責者。委派與持續的背景工作需要
  使用者明確授權。
- 從最小且明確的變更開始。新增機制前，先刪除或重複使用既有內容。
- 對於錯誤修正與實質行為，應在公開契約層級採用 TDD：紅燈 -> 最小綠燈
  -> 重構。不要為靜態接線或維持行為不變的刪除刻意製造測試。
- 讓發現結果修正做法。重新規劃受影響的部分，而不是遵循過時的
  預測。
- 將範圍維持在目標內。除非會阻礙驗證，否則相鄰的清理工作僅需回報。

### 驗證

- 執行儲存庫適用的測試、型別檢查、lint、建置與靜態檢查。
- 透過實際進入點操作實質行為。檢查預期用法，以及一條
  可信的失敗或復原路徑。
- 依據目標、護欄與可信風險審查結果。驗證是
  證據，而非完成檢查清單後的收據。
- 一旦失敗，就將其作為下一個行動。修正並重複，直到所有退出條件都通過。

## 界線

- 只有在涉及保留給使用者決定的實質事項，或不可逆的正式環境、
  法律／隱私、破壞性或高安全性操作時才詢問。
- 對目前由使用者擁有的功能分支，可直接提交、推送、執行 rebase，並在需要時使用
  `--force-with-lease`，無須再次詢問許可。未經明確許可，絕不可合併、使用一般的 `--force`、
  建立額外的 PR，或改寫預設、共用、他人擁有或正由他人並行使用的分支。
- 在 main/master/develop 分支上編寫程式碼前，請使用
  `scripts/mux-worktree.sh <type>/<branch-name>` 建立隔離的 worktree。[精神：Worktree 隔離]
- 耗時或高度未知的工作可將目前的假設、證據、偏差與
  暫停觸發條件記錄於被 git 忽略的 `.context/implementation-notes.md`。短期工作則保留在
  對話中。

## 完成

在要求的終點停止：回答；操作類工作預設提交並推送；明確要求的本機變更或僅提交；PR；或完整
交付。不要僅因某個規劃步驟完成就停止。只有在具體的驗證或交付分支需要詳細指令時，
才參閱 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/development-lifecycle/REFERENCE.md)。
