透過由分流角色組成的小型狀態機，在追蹤系統中推進議題。

當儲存庫將外部提取要求視為請求介面時（請參閱追蹤系統設定），分流也會涵蓋這些提取要求：**PR 是附帶程式碼的議題**——使用相同的角色、狀態與狀態機，差異會在下文以「若為 PR」標示。請依追蹤系統將單獨的 `#42` 解析為議題或 PR。

探索程式碼庫時，請使用專案的領域詞彙表，讓標題、留言與代理程式簡報符合專案用語。遵循受影響區域的 ADR。外部或目前行為請使用 `/read-the-damn-docs`，有相互競爭的修正計畫時使用 `/plan-arbiter`，大型史詩任務則使用 `/visual-plan`。

## AI 免責聲明

分流期間張貼到追蹤系統的每則留言，**必須**以以下內容開頭：

```
> *This was generated by AI during triage.*
```

## 議題追蹤系統

透過 `git remote -v` 與儲存庫慣例偵測：

- **GitHub**（遠端為 `github.com`）→ 使用 [`gh`](https://github.com/malinskibeniamin/skills/blob/main/triage/tracker-github.md)
- **Jira**（分支或提交中有 Atlassian 格式的工單 ID，或有 `.atlassian/` 設定）→ 使用 [`acli`](https://github.com/malinskibeniamin/skills/blob/main/triage/tracker-jira.md)

兩者皆存在（GitHub 儲存庫與 Jira 工單）→ 詢問使用者要在哪一個系統建立或分流。

## 角色

兩種**類別**角色：

- `bug`——有功能故障
- `enhancement`——新功能或改善

五種**狀態**角色：

- `needs-triage`——維護者必須評估
- `needs-info`——等待回報者提供更多資訊
- `ready-for-agent`——規格完整，可供離線代理程式處理
- `ready-for-human`——需要由人員實作
- `wontfix`——不會採取行動

每個已分流的議題都必須恰好具有一個類別角色與一個狀態角色。若狀態衝突，請標示並在採取行動前詢問。

以上為標準角色名稱。追蹤系統中的實際標籤或狀態字串可能不同——若有差異，請根據專案現有的標籤或狀態推斷；詢問一次後，在工作階段內記住對應關係。

## 顯示需要注意的項目

查詢追蹤系統。顯示以下三個分類，各分類依時間由舊至新排列：

1. **未加標籤／無狀態**——從未分流
2. **`needs-triage`**——正在評估
3. **自上次分流紀錄後回報者有活動的 `needs-info`**——需要重新評估

若 PR 在範圍內，請將外部 PR 納入這些分類，並在每一行標示 `[PR]` 或 `[issue]`。探索介面只顯示*外部* PR（由追蹤系統設定定義哪些人屬於外部）——協作者尚在進行中的 PR 不屬於分流工作。此篩選條件只適用於探索；明確指定的 PR 無論作者是誰都必須分流。

顯示數量與每個項目的一行摘要。讓維護者選擇。

## 分流特定議題或 PR

1. **蒐集脈絡。** 閱讀完整議題或 PR（內文、留言、標籤／狀態、回報者、日期；若為 PR，也要閱讀差異）。解析先前的分流紀錄，避免再次詢問已解決的問題。使用專案的領域詞彙表探索程式碼庫，並遵循該區域的 ADR。進行兩項程式碼庫檢查：(a) **重複性**——依領域概念搜尋所請求行為的現有實作（不只搜尋請求中的措辭），並回報搜尋位置；若找到，則視為已實作並設為 `wontfix`（步驟 5）。(b) **先前拒絕紀錄**——閱讀 `.out-of-scope/*.md`，找出並呈現任何與此請求相似的內容。

2. **提出建議。** 向維護者說明建議的類別與狀態及其理由，並提供與請求相關的程式碼庫簡短摘要，包括是否已實作。等待指示。

3. **驗證主張。** 在深入詢問前，先確認主張是否成立。若為錯誤，依回報者提供的步驟重現。若為 PR，確認差異是否達成其宣稱的效果：簽出該 PR，執行相關測試或指令。回報結果——已透過程式碼路徑確認、驗證失敗，或細節不足（這是強烈的 `needs-info` 訊號）。經確認的驗證能讓代理程式簡報更有力。如需進行根本原因調查與 TDD 修正計畫，請參閱 [REFERENCE.md#tdd-fix-plan-mode](https://github.com/malinskibeniamin/skills/blob/main/triage/REFERENCE.md)。

4. **深入詢問（如有需要）。** 若議題需要補充細節，且領域用語或 ADR 很重要，請執行 `/grilling`。

5. **套用結果：**
   - `ready-for-agent` → 張貼代理程式簡報留言（[AGENT-BRIEF.md](https://github.com/malinskibeniamin/skills/blob/main/triage/AGENT-BRIEF.md)）
   - `ready-for-human` → 使用相同結構，但註明無法委派的原因
   - `needs-info` → 張貼分流紀錄（請參閱 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/triage/REFERENCE.md)）
   - `wontfix`（已實作）→ 指出實作在程式碼庫中的位置；**不要**寫入 `.out-of-scope/`（該知識庫用於*遭拒絕*的請求，而非已建置的功能），然後關閉
   - `wontfix`（錯誤）→ 提供禮貌說明，然後關閉
   - `wontfix`（功能增強）→ 寫入 `.out-of-scope/`，在留言中加入連結，然後關閉（[OUT-OF-SCOPE.md](https://github.com/malinskibeniamin/skills/blob/main/triage/OUT-OF-SCOPE.md)）
   - `needs-triage` → 套用角色；若已有部分進展，可選擇加入留言

## 快速覆寫狀態

使用者說「將 #42 移至 ready-for-agent」→ 信任其指示，確認即將執行的動作（變更角色、留言、關閉），然後執行。略過深入詢問。若未經深入詢問工作階段就移至 `ready-for-agent`，請詢問是否要撰寫代理程式簡報。

## 繼續先前的工作階段

若議題上已有先前的分流紀錄，請閱讀紀錄，檢查回報者是否已回答尚待處理的問題，並在繼續前呈現更新後的情況。不要再次詢問已解決的問題。
