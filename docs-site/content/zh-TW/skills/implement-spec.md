當下方工作流程需要模型可呼叫的技能時，請為每個相依技能分別呼叫 Skill 工具。沒有此工具的宿主應依[相依技能載入規則](https://github.com/malinskibeniamin/skills/blob/main/writing-for-agents/SKILL-MECHANICS.md#loading-dependencies)完整閱讀標準 `SKILL.md`。僅供使用者呼叫的技能應建議由使用者執行，不要自動呼叫。

你已取得一份規格。這份規格應附有工單，說明如何實作該規格。

僅為已核准、具有實際阻擋關係且工單可獨立驗證的規格選擇此技能，不用於一般的單一工單任務。使用者呼叫此技能即代表明確要求委派並使用平行代理程式；載入或提及此技能不代表同意委派。

若存在 `CLAUDE.md`，請先閱讀 `CLAUDE.md`；否則閱讀 `AGENTS.md`。依照其中的問題追蹤器指引操作。若沒有，請告知使用者執行 `/work-automation-kit`。

目標是在單一**整合分支**上實作整份規格，並依問題追蹤器結案的方式解決每張工單。

工單不是步驟清單，而是具有阻塞關係的**任務圖**。這表示總會有一個由已就緒工單組成的**前沿**可供領取。

與子代理程式之間的溝通應精簡。主要透過**脈絡指標**溝通：指向規格、工單、研究筆記與先前的提交。不要重複透過指標即可取得的資訊。

盡可能在背景執行**實作子代理程式**，以達到**最大並行度**。

## 步驟

1. 閱讀規格與工單。閱讀到足以理解任務圖為止。

2. （選用）使用**探索子代理程式**進行工單所需的探索——相關程式碼檔案或外部文件。確保探索子代理程式可以儲存檔案——它應將 Markdown 筆記儲存在儲存庫以外、所有後續子代理程式都能存取的目錄中。這讓**實作子代理程式**專注於實作而非探索。

3. 建立整合分支。若問題追蹤器透過 PR 結案，或使用者要求 PR，請在步驟 5 首次合併後開啟草稿 PR（沒有領先 main 之提交的分支無法開啟 PR），並標記為關閉該規格與工單。

4. 使用**實作子代理程式**實作每張工單，每個子代理程式在各自的工作樹與分支上作業。每個實作子代理程式：
   - 開始前確認其工作樹以整合分支為基礎，若不是則重設至整合分支上；
   - 呼叫 Skill 工具並傳入 "tdd" 來建置該工單；
   - 回報完成前將整合分支的最新提交合併到自己的分支，讓步驟 5 成為快轉合併。

5. **實作子代理程式**完成後，由**合併子代理程式**將其工作合併到整合分支。

6. 若這改變了可用工單的**前沿**，就為新工單啟動更多**實作子代理程式**。這樣可以達到最大並行度。

7. 所有工單完成後，呼叫 Skill 工具並傳入 "review"，審查整合分支。在單一**實作子代理程式**中修正程式碼審查提出的所有問題。

8. 若已有草稿 PR，而使用者要求的端點是草稿，就維持草稿狀態；否則標記為可供審查。沒有 PR 時，依問題追蹤器結案的方式解決每張工單，並回報整合分支。

9. 清理所有**實作子代理程式**的工作樹。
