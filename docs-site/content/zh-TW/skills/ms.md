聚焦單一面向進行審查：這項變更是否值得現在交付、誰會受益，以及它是否為能驗證價值的最小
可回復變更。規則詳見 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ms/RULES.md)。

可針對 PR、分支、計畫或工單獨立執行，也可在每次 PR 審查時，於 `/review` 中以 **ms 審查角色**
執行。不會啟動任何代理。

## 類別 [#lanes]

每個 PR 只服務一個類別。讀取 PR 內文中的 `Lane:` 行；若缺少則自行推斷。

| 類別 | 值得投入時間的條件 | 所需證據 |
|---|---|---|
| 維持運作 | 減少繁瑣作業、風險或支出 | 消除的事故、警示或成本；回復方式 |
| 使用體驗改善 | 排除使用者的阻礙或維護聲譽 | 前後對照數據或可重現的失敗案例；誰有感 |
| 新增價值 | 讓明確的客群更有可能付費或繼續使用 | 受益對象、營收路徑、可交付的最小變更、預設關閉的上線方式 |
| 設計品味 | 避免代價高昂且不可逆的決策，或移除一個概念 | 避免的未來成本；為何現在處理比以後便宜 |

混合多種類別時應拆分，除非其中一項變更是另一項的必要前提。

## 流程 [#procedure]

1. **範圍：** PR 標題與內文、連結的工單、提交紀錄、差異。以差異為準，不以宣稱為準。
2. **分類：** 判定類別及涉及面向：營收路徑、客戶介面、契約/API、維運、
   文件、CI 或開發迭代流程、代理平台。
3. **提問：** 現在誰會遇到這個問題，又付出什麼代價？有哪些可觀察的證據能證明已完成？
   可回復的最小變更是什麼？哪些內容刻意排除在外？
4. **載入：** 對應的 [RULES.md](https://github.com/malinskibeniamin/skills/blob/main/ms/RULES.md) 章節。套用 S/A 級規則、明確的 B 級違規，
   以及僅限顯而易見的 C 級違規。
5. **評估營收可能性：** 高、中、低或無，並附上一項理由。對於
   維護、使用體驗改善或設計品味，只要有相應證據，評為「無」也沒問題。未知就維持未知；
   絕不捏造數字。

## 嚴重程度 [#severity]

- **P1：** 不實的成功結果、健康狀態或價格；將未知用量計為免費；免費使用者遭到封鎖
  或錯誤限制；客戶資料的處理超出預期；破壞契約卻沒有逐步推出計畫。
- **P2：** 沒有受益對象或類別；混合多種類別；未經量測的效能或 CI 宣稱；
  推測性的通用化設計；沒有可觀察的完成條件；文件與行為矛盾。
- **P3：** 措辭、命名，或未聲明顯而易見的類別。

價值面向的審查發現，絕不阻擋已確認的正確性或安全性修正。

## 排除項目 [#exclude]

- 由其他 `/review` 審查角色負責的正確性、安全性與風格。
- 策略否決：質疑適切性並指出缺少的證據；由負責人決定。
- 自動產生的檔案。

## 輸出 [#output]

`Lane: <lane> | Beneficiary: <who> | Revenue likelihood: <level> - <reason>`，接著輸出
`[P1|P2|P3] <rule-id> <file:line or PR body> <missing evidence> - <smallest fix>`。
此審查角色的輸出上限為 250 字。若未發現問題：
`APPROVED -- <lane>, <beneficiary>, value evidenced.`
