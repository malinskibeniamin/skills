三種模式，同一套價值標準。撰寫模式在撰寫當下為每個新增或修改的測試把關；`/tdd` 會導向這裡。稽核模式會針對下列測試進行重點檢查：重複驗證原始碼、重複較強的驗證、將行為與實作耦合，或讓正式程式碼中僅供測試使用的介面繼續存在。大範圍稽核應拆成各自範圍一致的後續 PR 持續進行；以提高信心為目標，而非追求刪除數量。專案模式會刪減整個子系統的測試範圍（套件、應用程式或核心領域所屬的每個測試檔案）；開始前，請閱讀 [CAMPAIGN.md](https://github.com/malinskibeniamin/skills/blob/main/test-audit/CAMPAIGN.md)。

## 撰寫關卡 [#authoring-gate]

新增任何測試前，先回答四個問題；只要有一個尚未回答，就先不要新增：

1. 它保護了什麼可觀察的行為、不變條件或獨立契約？
2. 什麼合理的迴歸問題會讓它失敗？
3. 為什麼既有的測試涵蓋範圍還無法捕捉這個失敗？每個契約都應在最有力的邊界上有一個主要負責測試；其他層若要新增測試，必須有自身獨特的風險，例如主要負責測試無法觸及的傳輸或生命週期失敗。優先擴充表格驅動案例或共用測試資料，而非新增近乎重複的測試；並在同一次變更中整併重複的設定。
4. 它是否需要任何正式程式碼呼叫端都不需要的介面（匯出、旗標、包裝函式、注入掛鉤）？若是，請改將測試移到真正的邊界。

接著，逐一依照所有[低價值模式](#junk-patterns)檢查測試；只要符合其中一項，就無法通過關卡，除非[保留標準](#retention-bar)明確指出它獨立守護的契約。在保持行為不變的重構下會失敗的測試，驗證的是實作而非行為；提交前，請先在負責該行為的邊界重新撰寫。

錯誤迴歸測試必須在修正前的程式碼上因預期原因而失敗，並在負責該行為的邊界完成修復後通過。從未實際證明會失敗的迴歸測試，證明的是模擬物件，而非修正有效。在負責該行為的邊界放置一個迴歸測試即可涵蓋該錯誤；不要在它經過的每一層重複相同情境。

## 低價值模式 [#junk-patterns]

所有模式共用的檢查清單：撰寫關卡會拒絕符合任一模式的新測試，稽核則會找出符合這些模式的既有測試。

- 沒有斷言、只用來增加涵蓋率的探測測試；
- 自我比較，以及原樣複製後再比對的測試；
- 複製的測試資料、清冊、資訊清單或匯出清單；
- 對原始碼、匯入或字串進行精確文字搜尋；
- 已在真正邊界重複驗證的私有判斷函式或呼叫形式測試；
- 對同一契約的重複呼叫；
- 在個別套件內重複驗證共用輔助函式；
- 唯一目的只是保留僅供測試使用的匯出、全域變數或包裝函式的測試；
- 唯一呼叫端是測試的無用正式程式碼；
- 由受測輔助函式或轉譯器產生的預期值；
- 自行實作所斷言行為的模擬物件，或用同一個完全相同的模擬物件代替不同 API；
- 由測試資料提供本應由負責元件產生的回執、准入結果或回呼順序，或對執行路徑從未寫入的儲存區斷言持久化結果；
- 只重述宣告旗標，卻未實際執行旗標所承諾的傳遞或確認行為的能力測試；
- 因無關原因而通過的負向對照測試，例如遭到另一個防護條件拒絕，或遭到正式執行路徑根本不會觸及的拒絕條件阻擋；
- 名稱或測試資料承諾的範圍超出輸入實際驗證的範圍，例如名為「停用視窗」的測試，卻只斷言視窗未被清除。

## 價值標準 [#value-bar]

測試應透過保護行為、防範合理的迴歸問題，或守護具獨立意義的契約，來證明其維護成本值得。在稽核中，若既有測試必須隨著保持行為不變的原始碼重整而修改，就值得懷疑，但不代表可以直接刪除；撰寫關卡仍會拒絕新增這類測試。

評估候選項目前，請完整閱讀測試、負責該行為的正式程式碼、其進入點、呼叫端、被呼叫端、同類實作、重疊的測試、CI 執行路由，以及相關歷史。先閱讀根目錄與適用範圍內的 `AGENTS.md` 或 `CLAUDE.md` 檔案。若測試聲稱驗證的是由相依套件支援的行為，請直接檢查該相依套件的原始碼或型別。

## 探索 [#discovery]

探索階段應維持唯讀，並在編輯前回報證據。若範圍較廣，請將探索分成幾條工作線：核心與套件、應用程式與 UI、指令碼與工具，以及一次跨領域模式掃描。只有在使用者明確要求委派或 `/swarm` 時，才平行執行各工作線；否則請依序進行。

在專案模式之外，優先選擇少數高信心的候選項目，而非列出大量推測性清單。找出[低價值模式](#junk-patterns)。

## 保留標準 [#retention-bar]

若測試獨立守護公開 API、SDK、通訊協定、設定、遷移、儲存、安全性、平台、預設值、提示詞位元組、跨語言產生內容、套件、發布或架構契約，請保留它。也請保留：

- 順序屬於可觀察行為時的呼叫順序測試；
- 具有合理失敗模式的迴歸測試；
- 作為成本最低的獨立防護手段的原始碼檢查：契約（使用者可見的鍵、位元組或路徑）改變時會失敗，而僅修改識別名稱的重構不會使它失敗；
- 在基準版本上失敗、原本應保留的測試：將它視為可能的產品錯誤，以 `/diagnosing-bugs` 重現，並修復負責該行為的元件，而非刪除測試。

靜態檢查或執行緩慢都不是刪除理由。看似驗證實作的測試，仍可能是獨立的契約驗證；移除前，請先證明並非如此。

## 候選項目證據 [#candidate-evidence]

編輯前，請記錄以下每個欄位。只要缺少任何欄位，該候選項目就尚未準備好刪除：

- 確切的測試名稱與位置；
- 它實際能偵測到的失敗；
- 所涵蓋的正式程式碼介面或支援介面的非測試呼叫端；
- 刪除後仍保留、位於負責邊界且更有力的驗證，或不需要驗證的理由；
- 相關歷史，以及測試或介面存在的原因；
- 此次刪除可一併移除的正式程式碼或測試支援程式碼；
- 風險與針對性的驗證指令。

## 編輯範圍 [#edit-shape]

選擇一批範圍一致、屬於同一負責邊界的變更。刪除過時且僅供測試使用的匯出、全域變數、包裝函式，以及無用的正式執行路徑，不要保留別名。將保留的迴歸測試移至其正式歸屬的元件。將重複的套件或相依套件斷言整併為一個通用契約。

優先讓正式程式碼行數淨減少。不要新增重述相同實作的替代測試，也不要為了增加刪除數量，就將尚不確定的候選項目當成清理項目。

## 驗證 [#validation]

1. 刪除或移動測試前，先停止測試監看程序；橫跨刪除操作的監看輸出不能作為證據。
2. 使用儲存庫的針對性指令，執行負責元件與同類元件的最小範圍測試，例如 `bunx vitest run <path>` 或 `go test ./<pkg>`。
3. 對於移除的原始碼文字搜尋或計畫斷言，請執行負責真實契約的可執行指令碼或試執行。
4. 執行 `bun run lint:fix`、`bun run type:check`、`git diff --check`，以及 CI 對變更檔案執行的關卡檢查。
5. 檢查 `git diff --numstat`；將正式程式碼／工具與測試及測試支援程式碼分開回報。
6. 完成最後的稽核編輯後，執行 `/review`。

## 提交與後續作業 [#landing-and-continuation]

透過 `/commit-push-pr` 提交，並以使用者要求的階段為止；合併需要明確許可。一次提交一個範圍一致的 PR；合併後，從預設分支更新，並為下一批高信心變更重新執行唯讀探索。

## 交接 [#handoff]

回報根本原因與已移除的低價值類別；負責該行為的正式程式碼簡化內容；保留的誤判項目及其仍有價值的原因；實際執行的針對性與完整驗證；正式程式碼與測試的行數；PR 與合併狀態；明確列出的後續工作。
