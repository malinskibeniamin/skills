由使用者叫用的完整交付端點。持續作業，直到要求的成果完成發布且驗證無誤，或有證據顯示確實遭遇外部阻礙。

## 結束條件

根據要求與儲存庫的即時狀態確認以下項目：

- **目標**：要發布的行為或變更。
- **限制條件**：分支、隱私、破壞性操作，以及使用者保留的界線。
- **驗證**：儲存庫檢查，以及在實際進入點可觀察到的行為。
- **交付**：要求的提交、遠端分支、PR 與 CI 狀態。
- **停止條件**：所有條件皆通過，或外部相依項目使作業無法繼續。

## 迴圈

**檢查 -> 驗證 -> 修復 -> 重複**，直到驗證通過。

1. 檢查完整的分支差異與要求的端點。納入已提交、已暫存、
   未暫存及未追蹤的工作；不要發布不相關的檔案。
2. 執行所有適用的儲存庫原生檢查。前端工作通常包括聚焦範圍的
   測試、`bun run type:check` 與 `bun run lint:fix`；Go 工作則包括文件中指定的測試、
   vet 與建置檢查。
3. 透過每項重大且可執行變更的實際使用者或公開進入點進行操作。
   檢查預期用途，以及一個可信的故障或復原路徑。測試不能取代這項操作。
4. 對面向客戶的介面，檢查呈現結果或終端機輸出、重要
   狀態、無障礙功能、主控台／錯誤，以及相關的檢視區或平台風險。
5. 依據目標、限制條件、語意密度與可信風險審查一次。
   修復具體發現的問題，接著讓受影響的證據失效並重新執行驗證。
6. 如果變更宣稱具有可衡量的影響，請以相同的基準／候選情境重複測量。
   若不存在有助於決策的衡量方式，請勿虛構基準測試。

針對相依套件版本升級，請依據目前的第一手文件驗證鎖定檔、全新安裝／建置，以及每個
受影響的呼叫位置。

請勿刻意製造第二次審查、清理作業、技能叫用或代理程式呼叫。在主要脈絡中維持
單一負責人。
使用不同模型或委派的作業管道需要使用者明確授權。

## 交付

依照 [commit-push-pr/REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md) 進行明確的暫存、
提交格式設定、推送、建立草稿 PR、審查者指引及撰寫 PR 內容。對目前由使用者擁有的功能分支，可執行 rebase，並在需要時使用
`--force-with-lease`，無須再次詢問許可。未經明確許可，絕不可合併、使用一般的 `--force`，或改寫預設、共用、
他人擁有或正由他人並行使用的分支。

如果 `gh stack view --json` 識別出堆疊，請以其父層為基準審查並驗證目前層。
只有在透過 `/stacked-prs` 明確要求時，才發布整個堆疊；一般
PR 端點不得發布其他尚未提交的層。

- 將審查與驗證綁定至目前的 `HEAD`；後續編輯會使該證據失效。
- 只有因為此命令是明確的完整交付端點，才監控 CI。修復
  失敗項目、重新執行受影響的驗證、推送，然後繼續。
- 解決所有現有的人工作業審查討論串；`pr-feedback-completeness-stop` 會強制要求
  未解決項目數為零。人工回饋沒有數量上限。解決目前這批回饋後，
  請勿輪詢未來的回饋。
- 自我審查一旦無問題就立即停止。反覆出現雜訊般的發現，代表應交接處理，
  而不是任意增加審查輪次。
- 額外摘要、歷史記錄清理或後續成果需要明確要求。

## 完成

- 已在實際進入點觀察到要求的行為，或已記錄無法執行的原因。
- 目前 `HEAD` 上的適用檢查皆通過且沒有警告。
- 目前的人工回饋皆已解決。
- 要求的提交、推送、PR 與 CI 端點皆已存在。
- 未隱藏任何未提交或未追蹤的工作。
- 最終回覆包含證據，並以恰好一行狀態結尾。

在預設分支上，交付前請使用
`scripts/mux-worktree.sh <type>/<name>` 建立隔離的工作樹。[ETHOS：工作樹隔離]
