由使用者叫用的完整交付端點：持續作業，直到驗證無誤或確實遭遇外部阻礙。

## 結束條件

確認目標、無法推斷的限制條件、儲存庫檢查與實際進入點行為、要求的提交／遠端／PR／CI 交付，以及停止條件。

## 迴圈

檢查 -> 驗證 -> 修復 -> 重複，直到驗證通過。

1. 檢查完整的分支與端點：已提交、已暫存、未暫存及未追蹤的工作。排除不相關的檔案。
2. 執行儲存庫原生檢查。前端工作通常包括聚焦範圍的測試、`bun run type:check`、`bun run lint:fix`；Go 工作則使用文件中指定的測試、vet 與建置檢查。
3. 透過每項重大且可執行變更的實際使用者或公開進入點進行操作，包括一個可信的故障或復原路徑。測試不能取代這項操作。
4. 對面向客戶的介面，檢查呈現結果或終端機輸出、狀態、無障礙功能、錯誤，以及相關的檢視區／平台。所有可見變更皆須套用 [PR 視覺證據關卡](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md#frontendcustomer-facing-detection--screenshot-table-phase-5)。
5. 依據目標、限制條件、語意密度與可信風險審查一次。修復問題、使受影響的證據失效，並重新執行驗證。
6. 如果變更宣稱具有可衡量的影響，請以相同的基準／候選情境重複測量；請勿虛構無用的基準測試。

針對相依套件版本升級，請依據目前的第一手文件驗證鎖定檔、全新安裝／建置，以及每個受影響的呼叫位置。

請勿刻意製造審查、清理作業、技能或代理程式呼叫。在主要脈絡中維持單一負責人；使用不同模型需要使用者明確授權。

## 交付

依照 [commit-push-pr/REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/commit-push-pr/REFERENCE.md) 進行暫存、提交、推送、建立草稿 PR、指定審查者及撰寫內容。對目前由使用者擁有的功能分支，可執行 rebase，並在需要時使用 `--force-with-lease`，無須再次詢問許可。未經明確許可，絕不可合併、使用一般的強制推送，或改寫預設、共用、他人擁有或正由他人並行使用的分支。

如果 `gh stack view --json` 識別出堆疊，請以其父層為基準驗證目前層。只有明確要求 `/stacked-prs` 時，才發布整個堆疊。

- 將證據綁定至目前的 `HEAD`；後續編輯會使其失效。
- 此明確的完整交付端點會監控 CI。修復失敗項目、重新執行驗證、推送，然後繼續。
- 解決所有目前的人工作業審查討論串；`pr-feedback-completeness-stop` 會強制要求完成。人工回饋沒有數量上限。解決目前這批回饋後，請勿繼續輪詢。
- 自我審查一旦無問題就立即停止。反覆出現雜訊般的發現，代表應交接處理，而不是任意增加審查輪次。
- 額外摘要／後續成果與歷史記錄清理需要明確要求。

## 完成

- 已在實際進入點觀察到行為，或已記錄無法執行的原因。
- 目前 `HEAD` 上的適用檢查皆通過且沒有警告。
- 目前的人工回饋皆已解決；要求的提交／推送／PR／CI 皆已存在。
- 未隱藏任何工作；最終回覆包含證據，並以恰好一行狀態結尾。

在預設分支上，交付前請使用 `scripts/mux-worktree.sh <type>/<name>` 建立隔離的工作樹。[ETHOS：工作樹隔離]
