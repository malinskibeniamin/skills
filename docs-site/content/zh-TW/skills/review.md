從固定點到 `HEAD` 產出診斷成品。除非使用者明確要求發布，否則請勿編輯、提交、推送、
回覆、解決問題或張貼留言。
主要情境中只保留一位負責人；代理程式需要明確委派。
## 檢閱契約
- **目標**：判斷差異是否在沒有可信缺陷的情況下，達成所要求的結果。
- **護欄**：只回報由差異引入且可採取行動的發現；將已有文件記載的
  標準與產品／規格缺口分開處理；將產生的檔案視為證據，而非編輯
  目標。
- **驗證**：將主張追溯至來源。親自透過實際進入點試用每項可執行的變更；
  自動化測試是輔助證據，無法取代實際體驗證據。
- **停止條件**：每個適用介面都已納入檢查，且每項發現都有證據、
  後果、優先級，以及具體修正方式。
如果缺少固定點，詢問要以什麼作為檢閱基準。否則，先解析目前的 PR 層；這會在遠端主幹之前，選取堆疊式 PR 的父層：
```bash
BASE=$(PR_BASE_REF="${REVIEW_BASE:-}" "${CLAUDE_PLUGIN_ROOT:-.}/scripts/resolve-pr-base.sh")
git diff "$BASE"...HEAD
git log "$BASE"..HEAD --oneline
```
## 證據迴圈
**檢查 -> 驗證 -> 分類 -> 統整。**
### 檢查
1. 閱讀請求或規格、儲存庫指示、完整差異，以及相關
   呼叫位置。不要盲信 PR 摘要而忽略程式碼。
2. 對每項變更後的假設，跨越相關的
   產生端、型別或結構描述、儲存層、使用端與公開介面，反向追溯至權威來源。依領域概念、
   資料欄位及輸出值搜尋，而不只是搜尋變更的符號。
3. 使用相關的未變更程式碼、目前基準、近期歷史、測試資料或執行時期輸出等獨立成品，
   驗證出乎意料的主張。將差異中的註解視為假設，而非證據。
4. 比較測試資料與正式環境的資料形態，並建構一個行為反例，
   將預期欄位或狀態與其他位置可能發生的碰撞區分開來。
   對權限與可見介面建立對照；略過由格式化工具管理的樣式及既有缺陷。
5. 詢問：即使測試通過且程式碼看似符合請求，還可能有什麼問題。
### 驗證
- 以原始碼、結構描述、目前的主要文件或最小可執行檢查來重現主張。
- 使用具代表性的實際規模資料，操作預期路徑，以及一條可信的失敗或復原路徑。
  親自觀察主控台／網路／記錄與回應時間；測試絕不能取代實際使用。
- 若不存在安全的可執行環境，請說明阻礙因素與所需證據；將該行為維持為
  未驗證，而非推斷成功。
- 檢查測試完整性：公開行為、修正前是否正確失敗、斷言是否有意義、
  覆蓋率是否未被削弱，以及是否不存在容易不穩定的固定時間等待。
- 依必要行為、語意密度、領域清晰度、可信風險及已證實的規模，
  檢驗每個輔助函式、分支、相依套件、選項及檔案。
優先處理跨邊界矛盾，而非局部潤飾。
絕不以程式碼行數為最佳化目標，也不鼓勵程式碼高爾夫；應透過減少概念來維持清晰度。

只有在差異提供相關證據時，才加入特定介面的審查：
| 介面 | 檢查項目 |
|---|---|
| 面向客戶的 UI／CLI／報告 | 實際呈現的行為、關鍵狀態、文案、鍵盤操作／無障礙功能、主控台、相關檢視區 |
| 安全性／隱私／資料遺失 | 信任邊界、授權、機密資訊、注入、不可逆路徑與復原路徑 |
| API／結構描述／SQL／PostgreSQL | 相容性、資源語意、遷移安全性、產生的輸出、實際方言 |
| Go／並行處理／工作流程 | 所有權、取消、錯誤、競爭條件、重試、冪等性 |
| 相依套件／外部 API | 目前的主要文件、版本相容性、鎖定檔、安全公告 |

### 分類

每項發現都必須由差異引入；會影響使用者或破壞契約；
可重現或有具體路徑支持；標註在最精確的變更行；並
附上最小且安全的修正方式與驗證指令。

- **P0**：阻擋合併的暴露風險、資料遺失、服務中斷、核心流程無法完成，或缺少
  必要行為。
- **P1**：一般使用者會遇到的缺陷、迴歸、契約／規格遭破壞、誤報成功，或重大
  無障礙問題。
- **P2**：實用、範圍明確且影響較低的修正。
- **P3**：可選的未來改善或潤飾；預設不納入行內留言。

沒有測量結果或結構性上限，就不要提出效能發現。沒有可信風險，
就不要提出邊界案例發現。有證據支持的合理否決也是有效結論。

### 統整

依根本原因去除重複項目，並保留證據所支持的最高優先級。發現應置於收件資訊之前，且是主要
輸出；不要加入讚美、差異重述、要求重述或流程敘述。重新檢閱時，依新提交點將先前每項發現
標記為已修正、未解決或不再適用。

## 深入模式

針對 `/review --deep` 或高風險發布稽核，使用相同迴圈並建立完整的適用性清冊。
加入結構邊界、安全性／相依套件工具、每個
已變更的公開介面，以及確切的驗證證據。閱讀
[DEEP-AUDIT.md](https://github.com/malinskibeniamin/skills/blob/main/review/DEEP-AUDIT.md)；請勿加入自動代理程式、模型評審小組或技能鏈。

## 輸出

閱讀 [REFERENCE.md](https://github.com/malinskibeniamin/skills/blob/main/review/REFERENCE.md)，了解優先級用語與可直接用於留言的結構描述。
回報 `[P0|P1|P2] <file:line> <title> - <evidence, consequence, correction, verify command>`。
接著附上 `entrypoint, data, actions, observations, timing, limits`、固定點、模式、
發現數量、判定與剩餘限制。

若審查沒有發現，只回報判定與剩餘限制。張貼留言
需要使用者明確表達意圖；否則只回傳可直接用於留言的文字。
