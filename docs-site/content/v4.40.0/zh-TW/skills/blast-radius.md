找出變更除了差異內容之外還可能破壞哪些部分。列出呼叫端只是偵察，並非結果。結果應是能證明此變更安全的那項事實，並盡可能直接地加以驗證。

## 契約

- **固定點：** 除非呼叫端提供其他時間點，否則請檢查指定的基準版本到目前工作狀態之間的完整範圍。
- **界線：** 檢查非局部契約並執行驗證；不要編輯產品程式碼。
- **問題：** 哪個隱藏的使用端、生命週期、傳輸格式、共享狀態或外部契約，可能使這項變更造成缺陷？

## 證明階梯

以成本最低的方式，將每項安全事實沿著此階梯往下推進：原始碼行 -> 逐步檢驗的反例 -> 可執行的指令碼或測試 -> 實際執行中的進入點。尚未達到可執行證明的主張是**未證明**，不能因有信心就視為安全。

## 流程

1. 閱讀完整變更、異動的符號、呼叫位置、產生端、使用端、結構描述及公開介面。說明哪些行為有所不同，包括隱含的時序與生命週期變化。
2. 指出關鍵安全不變量。優先選擇一項能排除多個推測性風險的事實，例如「此操作只會移除已過期的項目，除此之外不會產生任何作用。」
3. 查看符號搜尋無法涵蓋之處：序列化資料、資料庫欄位、功能旗標、其他程式語言、固定版本的函式庫原始碼、拆卸順序、重試、並行處理，以及透過設定觸及的呼叫端。
4. 建立最小且可信的失敗路徑。將已確認的風險與已檢查並排除的路徑分開。引用精確證據；只有在搜尋範圍完整時，搜尋不到結果才算是證據。
5. 透過實際程式碼證明不變量。如果一次性指令碼或聚焦於公開契約的測試是成本最低的可執行檢查，就加以使用。不要保留只是在重述原始碼文字的測試。
6. 如果可使用實際執行的使用者路徑，請透過 `/dogfood` 操作。記錄每項事實停留在證明階梯的哪一層。

## 輸出

- **變更：** 可觀察到的語意差異。
- **安全不變量：** 確切事實、證明階層、指令與觀察結果；否則標記為 `unproven`。
- **風險：** 失敗路徑、發生可能性、影響、證據，以及成本最低的檢查方式。
- **已排除：** 已檢查的路徑，以及用以排除疑慮的證據。
- **合併前：** 當不變量為假時會失敗的最小指令或重現步驟。

風險必須有證據支持且範圍明確。關鍵不變量獲得證明後，不要再誇大可能性清單。
