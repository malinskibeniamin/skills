找出变更在差异范围之外可能破坏的内容。列出调用方只是侦察，并非结果。真正的结果是直接证明该变更安全所依赖的那一个事实，并尽可能以最直接的方式加以验证。

## 契约

- **固定点：**除非调用方指定其他节点，否则审查从请求的基准到当前工作状态之间的全部内容。
- **边界：**检查非局部契约并运行验证；不要编辑产品代码。
- **问题：**哪些隐藏的使用方、生命周期、线上数据形态、共享状态或外部契约可能使此变更演变为缺陷？

## 证据阶梯

以尽可能低的成本，将每个安全事实沿此阶梯向下推进：源代码行 -> 逐步验证的反例 -> 可执行脚本或测试 -> 实际运行的入口点。未达到可执行证明层级的主张都是**未经证明的**，不能仅凭信心认定为安全。

## 流程

1. 阅读完整变更、已变更符号、调用点、生产方、使用方、模式和公共接口。说明行为发生了哪些变化，包括隐含的时序和生命周期变化。
2. 明确关键安全不变量。优先选择一个能排除多项推测性风险的事实，例如“该操作仅删除已过期条目，除此之外不会产生任何影响。”
3. 查看符号搜索无法覆盖的地方：序列化数据、数据库列、功能开关、其他语言、固定版本的库源代码、清理顺序、重试、并发，以及通过配置间接触达的调用方。
4. 构建最小且可信的故障路径。区分已确认的风险与已经检查并排除的路径。引用确切证据；只有在搜索范围完整时，未找到结果的搜索才可作为证据。
5. 通过真实代码证明该不变量。如果一次性脚本或聚焦于公共契约的测试是成本最低的可执行检查，就添加它。不要保留仅仅复述源代码文本的测试。
6. 如果可以访问实际运行的用户路径，请通过 `/dogfood` 进行验证。记录每项事实在证据阶梯上到达的层级。

## 输出

- **变更：**可观察到的语义差异。
- **安全不变量：**确切事实、证据层级、命令和观察结果；否则标记为 `unproven`。
- **风险：**故障路径、可能性、影响、证据和成本最低的检查方式。
- **已排除：**已检查的路径以及用于排除这些路径的证据。
- **合并前：**当不变量为假时会失败的最小命令或复现步骤。

确保风险有证据支持且范围明确。关键不变量得到证明后，不要再夸大或罗列各种可能性。
