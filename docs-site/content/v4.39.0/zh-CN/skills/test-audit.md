三种模式，同一套价值标准。编写模式在编写时对每个新增或修改的测试进行准入检查；`/tdd` 会转到此处。审计模式有针对性地排查以下测试：重复断言源码、重复更强的验证、将行为与实现耦合，或让专供测试使用的生产代码接口持续存在的测试。范围较广的审计应拆分为独立且逻辑完整的后续 PR；以提升可信度为目标，而非追求删除数量。专项模式精简整个子系统的测试范围（某个包、应用或核心领域所属的每个测试文件）；开始前，请阅读 [CAMPAIGN.md](https://github.com/malinskibeniamin/skills/blob/v4.39.0/test-audit/CAMPAIGN.md)。

## 编写准入检查 [#authoring-gate]

添加任何测试之前，先回答四个问题；任何一个问题尚无答案，都意味着暂时不要添加：

1. 它保护了什么可观察行为、不变量或独立契约？
2. 哪种可信的回归问题会导致它失败？
3. 为什么现有覆盖无法捕获该故障？每个契约都应在验证能力最强的边界上有一个主要负责的测试；其他层需要有自身独特的风险，例如主要负责的测试无法触及的传输或生命周期故障。优先扩展表驱动用例或共享测试夹具，而不是添加近乎重复的测试；在同一次变更中合并重复的初始化设置。
4. 它是否需要任何生产调用方都不需要的生产代码接口（导出、标志、包装器、注入钩子）？如果需要，应将测试移到真实边界。

然后逐一对照所有[低价值模式](#junk-patterns)检查测试；只要匹配一项，就无法通过准入检查，除非[保留标准](#retention-bar)明确指出了它独立保护的契约。如果测试会因保持行为不变的重构而失败，它断言的就是实现，而非行为；提交前，应在负责该行为的边界上重写测试。

缺陷回归测试必须在修复前的代码上因预期原因失败，并在负责该行为的边界得到修复后通过。一个从未被证明确实失败过的回归测试，验证的是模拟对象，而不是修复。在负责该行为的边界上添加一个回归测试即可覆盖该缺陷；不要在它经过的每一层重演相同场景。

## 低价值模式 [#junk-patterns]

所有模式共用以下检查清单：编写准入检查会拒绝匹配其中任一项的新测试，审计则会查找匹配这些模式的现有测试。

- 不含断言、仅用于触发覆盖率的测试；
- 自我比较和原样复制；
- 复制的测试夹具、清单、清单文件或导出列表；
- 对源码、导入语句或字符串进行精确文本搜索；
- 已在真实边界得到验证的私有谓词或调用形式测试；
- 对同一契约的重复调用；
- 在包内重复测试共享辅助函数；
- 唯一目的就是保留测试专用导出、全局变量或包装器的测试；
- 仅被测试调用的无用生产代码；
- 由被测辅助函数或渲染器生成的预期值；
- 自行实现了被断言行为的模拟对象，或用同一个完全相同的模拟对象替代不同 API；
- 由测试夹具提供本应由负责该行为的代码产生的回执、准入结果或回调顺序，或针对执行路径从未写入的存储断言持久化结果；
- 重述已声明标志的能力测试，而不是实际验证该标志所承诺的交付或确认行为；
- 因无关原因而通过的阴性对照，例如被另一个防护条件拒绝，或使用生产执行路径根本无法到达的拒绝逻辑；
- 名称或测试夹具承诺的范围超出输入实际覆盖的范围，例如名为“停用窗口”的测试却在断言窗口未被清除。

## 价值标准 [#value-bar]

测试应通过保护行为、预防可信的回归问题或维护具有独立意义的契约，证明其维护成本是合理的。在审计中，如果现有测试必须随保持行为不变的源码重组而修改，就值得怀疑，但不能因此直接删除；编写准入检查仍应拒绝此类新测试。

评估候选项之前，应完整阅读测试及负责相关行为的生产代码，以及其入口、调用方、被调用方、同类实现、覆盖重叠的测试、CI 执行规则和相关历史。首先阅读根目录及适用范围内的 `AGENTS.md` 或 `CLAUDE.md` 文件。当测试声称验证了依赖项提供的行为时，应直接检查依赖项的源码或类型。

## 排查 [#discovery]

排查过程保持只读，编辑前先报告证据。范围较广时，将排查拆分为几条工作线：核心与包；应用与 UI；脚本与工具；一次跨领域模式扫描。只有用户明确要求委派任务或使用 `/swarm` 时，才并行执行这些工作线；否则按顺序执行。

在专项模式之外，优先选择少量高置信度候选项，而不是列出大量推测性条目。查找[低价值模式](#junk-patterns)。

## 保留标准 [#retention-bar]

当测试独立保障公共 API、SDK、协议、配置、迁移、存储、安全、平台、默认值、提示词字节、跨语言生成、包、发布或架构契约时，应予以保留。还应保留：

- 当调用顺序属于可观察行为时，对调用顺序的测试；
- 具有可信故障模式的回归测试；
- 当源码检查是成本最低的独立保障时，保留此类检查：契约（面向用户的键、字节或路径）发生变化时它会失败，而仅重构标识符时它仍能通过；
- 在基线版本上失败的保留测试：将其视为可能的产品缺陷，用 `/diagnosing-bugs` 复现，并修复负责该行为的代码，而不是删除测试。

静态检查或运行缓慢都不是删除理由。看似在验证实现的测试，仍可能承担独立契约的验证职责；删除前应证明并非如此。

## 候选项证据 [#candidate-evidence]

编辑前记录以下每个字段。任何字段缺失，都意味着该候选项尚不具备删除条件：

- 确切的测试名称和位置；
- 它实际能够检测到的故障；
- 被覆盖的生产代码或支持接口的非测试调用方；
- 删除后仍保留的、在负责该行为的边界上更强的验证，或无需验证的原因；
- 相关历史，以及该测试或接口存在的原因；
- 因此可以删除的生产代码或测试支持代码；
- 风险和针对性的验证命令。

## 编辑范围 [#edit-shape]

选择一组逻辑完整、围绕负责相关行为的边界展开的变更。删除过时的测试专用导出、全局变量、包装器和无用生产执行路径，不要保留别名。将保留的回归测试移到其应归属的位置。将重复的包或依赖项断言合并为一个通用契约。

优先让生产代码行数净减少。不要添加重述相同实现的替代测试，也不要为了增加删除数量，将尚不确定的候选项当作清理对象。

## 验证 [#validation]

1. 删除或移动测试前，停止测试监视进程；跨越删除操作产生的监视输出不能作为证据。
2. 使用仓库的针对性命令，运行负责相关行为的代码及同类代码的最小测试集，例如 `bunx vitest run <path>` 或 `go test ./<pkg>`。
3. 对于已删除的源码文本搜索或计划断言，运行负责真实契约的可执行脚本或试运行。
4. 运行 `bun run lint:fix`、`bun run type:check`、`git diff --check`，以及 CI 针对已更改文件运行的检查。
5. 检查 `git diff --numstat`；将生产代码和工具代码与测试及测试支持代码分开报告。
6. 完成最终审计编辑后，运行 `/review`。

## 提交与后续工作 [#landing-and-continuation]

通过 `/commit-push-pr` 推进到用户要求的终点；合并需要明确许可。每次推进一个逻辑完整的 PR；合并后，从默认分支更新代码，并针对下一批高置信度候选项重新执行只读排查。

## 交接 [#handoff]

报告根因和已删除的低价值类别；负责相关行为的生产代码的简化情况；保留的误报项及其仍有价值的原因；实际运行过的针对性验证和完整验证；生产代码与测试代码的行数；PR 和合并状态；明确列出的后续工作。
