提炼自 Bun 从 Zig 到 Rust 的 1.4 重写（https://bun.com/blog/bun-in-rust）：1,448 个文件、64 个并行智能体、11 天、1 名人类协调者、零删除测试。这些原则不依赖语言和模型——任何执行模型都适用（按照 CLAUDE.md 中的模型路由进行分配；跨模型审查与其他场景一样适用）。

## 1. 编写任何代码前先建立基线

- **冻结缺陷台账**：首先列出当前系统中的已知缺陷。重写后的问题分类必须能够区分“回归问题”和“一直存在的问题”。
- **对现有实现进行基准测试**：吞吐量、内存、二进制文件/包体积、延迟——使用相同的工作负载、相同的硬件，并记录具体数值。“感觉更快”不能作为证据。
- **统计测试数量**：立即记录断言总数；重写的退出门槛要求没有任何测试被跳过、弱化或删除。

## 2. 测试就是契约，应与实现无关

测试套件绝不能使用被替换的对象编写，也不能与其耦合。与语言无关的测试（例如针对 CLI/API 接口的 TypeScript 测试）能让你放心地替换底层引擎。如果测试套件存在耦合，首先解除耦合——这是第 0 阶段，而不是额外负担。

## 3. 先机械式转换，后惯用式重构

进行 1:1 转换——“如同通过转译器生成”——保留架构、命名和结构。只有在证明功能对等后，才能向惯用模式重构。同时进行两种转换（移植 + 重新设计）会导致每次失败的原因都模糊不清。如果临时桥接代码会存在得太久，则一次性重写优于增量重写；如果系统必须每周发布，则增量重写优于一次性重写——应谨慎选择并记录该决定。

## 4. 扩大规模前先试运行

在扩展到数百个文件之前，先使用完整流程（转换 -> 编译 -> 对抗式审查 -> 测试）端到端移植 3 个有代表性的文件。试运行用于校准提示词、审查清单和工作队列；扩大一个有缺陷的流程，只会扩大问题。

## 5. 将编译器/类型检查器作为工作队列

根据 `cargo check` 或 `tsc` 错误等经过排序的机械信号推进工作。
未进行委派时，由一名负责人按顺序开展工作。明确委派或使用
`/swarm` 后，在工作树中隔离相互独立的工作通道；每个通道只提交分配给自己的范围，
绝不暂存、重置或编辑其他通道的内容。

## 6. 使用全新上下文进行对抗式审查

实现者使用完整的代码库上下文；审查阶段从差异及其
契约出发，并假定转换可能有误。在重要的 PR 或交付节点，使用
仓库允许的前台跨模型审查。其他情况下，则使用全新的证据检查流程进行内联审查。

## 7. 语义等价性陷阱

看似相同的结构在不同技术栈中可能存在差异。应有针对性地排查：会在发布版本中消除副作用的断言/调试结构、整数溢出和边界检查差异、默认的复制与引用语义、递归/栈限制（使用深达数千层的异常嵌套输入进行测试）、区域设置/编码默认值。发现的每个陷阱都应转化为固定测试用例，而不只是记录在备注中。

## 8. 修复流程，而不是修复产物

当执行者生成有问题的代码时，不要手动修复——应修复生成该代码的提示词、检查清单或队列，然后重新运行。手动修复无法扩展到十个文件以后；流程修复则能覆盖剩余的一千个文件。人类的职责是：阅读验证报告、抽查、确认 CI 中没有跳过测试，然后执行合并。

## 退出门槛

- [ ] 所有重写前的测试均通过，零跳过/删除（比较断言数量）
- [ ] 在相同工作负载/硬件上，基准测试达到或超过已记录的基线
- [ ] 缺陷台账已分类：每个既有缺陷仍在跟踪，且没有出现新的回归类型
- [ ] 每个差异都经过对抗式审查（按照 CLAUDE.md 进行跨模型审查）
- [ ] 已记录回滚方案：在通过退出门槛之前，旧实现始终保持可发布状态
