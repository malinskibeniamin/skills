萃取自 Bun 1.4 從 Zig 到 Rust 的重寫（https://bun.com/blog/bun-in-rust）：1,448 個檔案、64 個平行代理、11 天、1 位協調者、零個遭刪除的測試。這些原則不受程式語言與模型限制——任何執行模型都適用（依照 CLAUDE.md 的模型路由進行分派；跨模型審查則一如其他情境適用）。

## 1. 撰寫任何程式碼前先建立基準

- **凍結缺陷清冊**：先列舉目前系統中的已知缺陷。重寫後的問題分類必須能區分「迴歸」與「原本就有問題」。
- **對現行實作進行效能測試**：吞吐量、記憶體、二進位檔／套件大小、延遲——使用相同的工作負載、相同的硬體，並記錄數值。「感覺比較快」並不是證據。
- **計算測試數量**：立即記錄斷言總數；重寫的完成門檻要求沒有任何測試遭到略過、弱化或刪除。

## 2. 測試就是契約，應與實作無關

測試套件絕對不能使用即將被取代的技術編寫，也不能與其耦合。與程式語言無關的測試（例如針對 CLI／API 介面執行的 TypeScript 測試）能讓你有信心地替換底層引擎。如果測試套件存在耦合，請先解除耦合——這是第 0 階段，而不是額外負擔。

## 3. 先機械式轉換，之後再慣用化

以 1:1 的方式轉換——「就像經過轉譯一樣」——保留架構、名稱與結構。只有在證明行為一致之後，才重構為符合慣用模式的實作。同時進行兩種轉換（移植與重新設計），會使每個失敗的原因都難以釐清。若暫時性的橋接程式碼將長期殘留，全面切換優於漸進式遷移；若系統每週都必須發布，則漸進式遷移優於全面切換——請審慎選擇並記錄決策。

## 4. 擴展至整個團隊前先試行

在擴展至數百個檔案前，先以完整流程（轉換 -> 編譯 -> 對抗式審查 -> 測試）端對端移植 3 個具代表性的檔案。試行可用來校準提示詞、審查清單與工作佇列；擴展有問題的流程，只會同步擴大問題。

## 5. 以編譯器／型別檢查器作為工作佇列

依據經過排序的機械式訊號推進工作，例如 `cargo check` 或 `tsc` 錯誤。
未進行委派時，由單一負責人依序處理。經過明確委派或使用
`/swarm` 後，請在工作樹中隔離彼此獨立的工作軌；每個工作軌只能提交其獲指派的範圍，
且絕不能暫存、重設或編輯其他工作軌的內容。

## 6. 以全新脈絡進行對抗式審查

實作者使用完整的程式碼庫脈絡；審查流程則從差異內容及其
契約開始，並假設轉換可能有誤。在非輕微的 PR 或發布節點，
使用儲存庫允許的前景跨模型審查。其他情況則透過全新的
證據檢視流程直接進行審查。

## 7. 語意等價陷阱

外觀相同的結構在不同技術棧中可能有不同行為。請刻意尋找：在發布版中會消除副作用的斷言／除錯結構、整數溢位與邊界檢查差異、預設的複製與參照語意差異、遞迴／堆疊限制（測試深達數千層的極端巢狀輸入）、語系／編碼預設值。每個發現的陷阱都應轉化為測試案例，而不是只留下一則備註。

## 8. 修正流程，而非產出

當執行代理產生不良程式碼時，不要手動修正——應修正產生該程式碼的提示詞／檢查清單／佇列，然後重新執行。手動修正無法擴展到第十個檔案之後；流程修正則能惠及剩餘的一千個檔案。人員的角色是：閱讀驗證報告、抽查、確認 CI 中沒有略過測試，並按下合併按鈕。

## 完成門檻

- [ ] 所有重寫前的測試皆通過，零個遭略過／刪除（比較斷言數量）
- [ ] 在相同工作負載／硬體上，效能測試達到或超越記錄的基準
- [ ] 缺陷清冊已完成分類：所有既有缺陷仍持續追蹤，且未出現任何新的迴歸類型
- [ ] 每個差異內容都已進行對抗式審查（依 CLAUDE.md 進行跨模型審查）
- [ ] 已記錄復原方式：在通過完成門檻前，舊實作仍可供發布
