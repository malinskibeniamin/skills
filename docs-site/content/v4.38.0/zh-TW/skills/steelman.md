反迎合。LLM 預設會表示認同。此技能強制提出反方論點。
略過偏好、目標、瑣碎操作、已由使用者證實的主張，以及實作工作，
除非涉及安全性、資料遺失或不可逆性，因而有必要提出異議。

## 程序

### 步驟 1：識別主張

用一句話重述使用者的主張。標記類型：
- **事實性**（可驗證：grep、文件、執行）-> 先驗證
- **因果性**（「X 因為 Y 而故障」）-> 測試其作用機制
- **架構性**（「模式 Z 無法擴充」）-> 探查現有用法
- **偏好／目標／範圍** -> 不進行 steelman。記錄 `noise`。返回。

偏好／目標由使用者決定。不進行 steelman。

### 步驟 2：蒐集證據

在提出論證*之前*，並行展開檢查：
- 以 Grep 搜尋具名符號／模式
- 閱讀所引用的檔案
- 若成本低，執行測試／命令
- 針對版本／工具相關主張，查閱文件／網路資料

不要根據泛泛而談的說法（「這個模式有問題」）提出論證。應以儲存庫中的證據為依據。

### 步驟 3：強化反方論證

使用具體參照，寫出最有力的反方論證：
- 必須有哪些條件成立，使用者才會是錯的？
- 儲存庫中有哪些證據支持使用者可能錯誤的情況？
- 使用者沒有考慮到哪種失敗模式？
- 有哪些先例與其主張矛盾（git blame、先前的提交、相關檔案）？

格式：2 至 4 個項目符號。每個項目都引用檔案:行號或命令輸出。

### 步驟 4：判定

三種結果：
- **確認**：證據支持使用者。附上參照並明確說明。依照使用者的計畫繼續。
- **反駁**：證據不支持使用者。附上參照並明確指出。讓使用者決定（覆寫或修正）。不要阻擋。
- **混合**：部分確認。指出哪些部分成立、哪些不成立。

## 反模式

不要：
- 詢問「你確定嗎？」-- 默默驗證，只呈現證據
- 在沒有參照的情況下唱反調 -- 僅以儲存庫內容為依據
- 阻擋使用者。呈現資訊，不要設關卡。
- 每一輪都進行 steelman -- 訊號會衰減。僅保留給高風險情況與明確邀請。

[精神：使用者可能犯錯。行動前先驗證。呈現證據，而非質疑。]
