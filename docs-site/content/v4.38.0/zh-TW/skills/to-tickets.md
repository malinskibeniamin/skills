將計畫、規格或對話拆分為一組**工單**——採用曳光彈式垂直切片，每張工單都會宣告**阻擋**它的其他工單。
如果 `CLAUDE.md` 存在，請先閱讀；否則閱讀 `AGENTS.md`。透過該檔案的 **Issue tracker** 指標解析追蹤器指示；絕不擅自假設文件路徑。如果檔案或指標皆不存在，請執行 `/work-automation-kit` 或使用其本機 Markdown 備援方案。
## 流程
### 1. 蒐集脈絡
使用對話脈絡中已有的所有資訊。如果使用者以引數傳入參考資料（規格路徑、議題編號或 URL），請擷取並完整閱讀其正文與留言。
### 2. 探索程式碼庫（選用）
如果尚未探索程式碼庫，請先進行探索，以了解程式碼目前的狀態。工單標題與說明應採用專案領域詞彙表中的用語，並遵循所修改區域的 ADR。
尋找可預先重構程式碼，讓實作更容易的機會。「先讓變更變得容易，再進行容易的變更。」
### 3. 草擬垂直切片
將工作拆分為**曳光彈**工單。
<vertical-slice-rules>
- 每個切片都會切出一條狹窄但完整、貫穿所有層級（結構描述、API、UI、測試）的路徑——採用垂直切片，而非單一層級的水平切片
- 完成的切片可以獨立示範或驗證
- 每個切片的規模都應能在一個全新的脈絡視窗中完成
- 任何預先重構都應先完成
</vertical-slice-rules>
為每張工單指定其**阻擋關係**——也就是必須先完成、該工單才能開始的其他工單。沒有阻擋項目的工單可以立即開始。
**大範圍重構是垂直切片的例外。**當一項機械式變更擴散至整個程式碼庫，且任何狹窄切片都無法獨立維持綠燈時，請按照擴展—收縮模式排序：先在舊形式旁**擴展**新形式，接著以可各自維持綠燈的批次**遷移**呼叫端，最後在所有遷移完成後刪除舊形式來**收縮**。每個遷移批次都受擴展工單阻擋；收縮工單則受所有遷移批次阻擋。如果遷移批次無法獨立維持綠燈，請使用整合分支，並讓它們全部阻擋最終的整合與驗證工單。
如果審查後仍有相互競爭的工單圖或切片策略，請執行 `/plan-arbiter`；若相依性圖較大，請發布 `/visual-plan`，讓阻擋項目與前沿工作可供檢視。
### 4. 詢問使用者
以編號清單呈現建議的拆分方式。每張工單需顯示：
- **標題**：簡短的描述性名稱
- **受阻於**：必須先完成哪些其他工單（如有）
- **交付內容**：此工單會使哪項端對端行為可運作
詢問使用者：
- 粒度是否合適？（太粗／太細）
- 阻擋關係是否正確——每張工單是否只相依於真正會阻礙它的工單？
- 是否應合併任何工單，或進一步拆分？
反覆調整，直到使用者核准拆分方式。
### 5. 將工單發布至設定的追蹤器
發布已核准的工單。具體**方式**取決於透過代理程式指示指標找到的追蹤器——無論使用哪種追蹤器，工單內容都相同，只有阻擋關係的呈現形式會改變：
- **本機檔案** -> 在 `.scratch/<feature-slug>/tickets/<NN>-<slug>.md` 為每張工單寫入一個檔案，依相依順序（阻擋項目優先）從 `01` 開始編號。每個檔案的「Blocked by」需列出其相依工單的編號與標題。使用下方的單張工單範本；絕不可將多張工單合併至同一個檔案。
- **實際的議題追蹤器（GitHub、Linear 等）** -> 依相依順序（阻擋項目優先）為每張工單發布一個議題，讓每張工單的阻擋關係可以參照實際識別碼。若平台支援，請使用其原生子議題關係表示父議題，並使用原生阻擋關係表示阻擋項目；否則，將每張工單的「Blocked by」設為阻擋它的議題。除非另有指示，否則套用 `ready-for-agent` 分流標籤——這些工單在設計上即可由代理程式領取。
請勿關閉或修改任何父議題。
處理**前沿工作**：也就是所有阻擋項目皆已完成的任何工單。對於完全線性的鏈結，這表示由上而下依序處理。
