此技能會根據已定案的對話脈絡與程式碼庫證據產出規格（有時稱為 PRD）。請統整資訊，不要重新討論已定案的決策。若缺少任何重大決策，請在「補充說明」中標示，而不要自行默認假設。

若 `docs/agents/` 中有議題追蹤系統與分流標籤的詞彙，請使用這些詞彙。若沒有，請在對話中回傳規格，並註明可選擇以 `/work-automation-kit` 作為後續設定步驟。

## 流程

1. 若尚未探索過儲存庫，請先探索，以了解程式碼庫的目前狀態。在整份規格中使用專案領域詞彙表的用語，並遵循相關範圍內的所有 ADR。

2. 規劃要在哪些接縫測試此功能。應優先使用現有接縫，而不是建立新接縫。盡可能使用最高層級的接縫。若需要新接縫，請在可行的最高層級提出。程式碼庫中的接縫越少越好，理想數量是一個。

若規格依賴目前的第三方或 API 行為，請執行 `/read-the-damn-docs`。若有多個可行的解決方案或接縫規劃，請執行 `/plan-arbiter`。只有在使用者要求額外的審查產出時，才使用 `/visual-plan`。

3. 使用下方範本撰寫規格。預設在對話中回傳；只有在使用者要求發布時，才將其發布至專案議題追蹤系統並套用 `ready-for-agent`。

4. 若使用者接下來希望拆分實作工作，請將核准的規格交給 `/to-tickets`。

</user-story-example>

**完成條件：**每項範圍內的行為、邊界與復原結果都對應至一則故事；不得有重複措辭、實作細節及範圍外的行為。

## 實作決策

列出已做出的實作決策。可包括：

- 將建置或修改的模組
- 將修改的模組介面
- 開發人員提供的技術釐清
- 架構決策
- 結構描述變更
- API 合約
- 特定互動

請勿包含特定檔案路徑或程式碼片段，因為它們可能很快就會過時。

例外：若原型產出的程式碼片段能比文字更精確地表達決策（狀態機、reducer、結構描述、型別形狀），請將其直接置於相關決策中，並簡要註明它來自原型。請精簡至富含決策資訊的部分——不要放入可運作的展示，只保留重要內容。

## 測試決策

列出已做出的測試決策。包括：

- 說明何謂良好的測試（只測試外部行為，不測試實作細節）
- 將測試哪些模組
- 測試的既有先例（也就是程式碼庫中類似類型的測試）
