将计划、规范或对话拆分成一组**工单**——采用示踪弹式垂直切片，每个工单都声明**阻塞**它的其他工单。
如果存在 `CLAUDE.md`，请先阅读它；否则阅读 `AGENTS.md`。通过该文件的 **Issue tracker** 指针确定工单跟踪系统相关说明；切勿假定文档路径。如果文件和指针均不存在，请运行 `/work-automation-kit` 或使用其本地 Markdown 回退方案。
## 流程
### 1. 收集上下文
基于对话上下文中已有的内容开展工作。如果用户将引用（规范路径、议题编号或 URL）作为参数传入，请获取该引用并完整阅读其正文和评论。
### 2. 探索代码库（可选）
如果尚未探索代码库，请进行探索以了解代码当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵循所涉及区域的 ADR。
寻找预先重构代码的机会，以降低实现难度。“先让变更变得容易，再完成这个容易的变更。”
### 3. 起草垂直切片
将工作拆分成**示踪弹**工单。
<vertical-slice-rules>
- 每个切片都要沿一条狭窄但完整的路径贯穿所有层（模式、API、UI、测试）——采用垂直切片，而不是针对某一层的水平切片
- 每个已完成的切片都能独立演示或验证
- 每个切片的规模都应控制在一个全新的上下文窗口内可以完成
- 任何预先重构都应优先完成
</vertical-slice-rules>
为每个工单注明其**阻塞关系**——必须先完成哪些其他工单，它才能开始。没有阻塞项的工单可以立即开始。
**大范围重构是垂直切片的例外。**当一项机械式变更扩散至整个代码库，并且无法通过任何狭窄切片保持构建正常时，请按扩展-收缩方式安排顺序：先在旧形式旁**扩展**出新形式，再分成各自保持构建正常的批次**迁移**调用方，最后在所有迁移完成后通过删除旧形式进行**收缩**。每个迁移批次都受扩展工单阻塞；收缩工单受所有迁移批次阻塞。如果迁移批次无法各自保持构建正常，请使用集成分支，并让它们全部阻塞最终的集成与验证工单。
如果评审后仍存在相互竞争的工单图或切片策略，请运行 `/plan-arbiter`；对于大型依赖关系图，请发布 `/visual-plan`，以便检查阻塞项和任务前沿。
### 4. 向用户确认
以编号列表形式展示提议的拆分方案。对于每个工单，请展示：
- **标题**：简短的描述性名称
- **受阻于**：必须先完成哪些其他工单（如有）
- **交付内容**：此工单实现的端到端行为
询问用户：
- 粒度是否合适？（过粗／过细）
- 阻塞关系是否正确——每个工单是否仅依赖真正构成其启动门槛的工单？
- 是否应合并某些工单或进一步拆分？
持续迭代，直到用户批准拆分方案。
### 5. 将工单发布到已配置的跟踪系统
发布已批准的工单。具体**方式**取决于通过智能体指令中的指针找到的跟踪系统——无论采用哪种方式，工单本身都相同，只有阻塞关系的呈现形式不同：
- **本地文件** -> 在 `.scratch/<feature-slug>/tickets/<NN>-<slug>.md` 中为每个工单写入一个文件，按依赖顺序（阻塞项优先）从 `01` 开始编号。每个文件的“受阻于”都列出它所依赖工单的编号和标题。使用下面的单工单模板；切勿将多个工单合并到一个文件中。
- **实际的议题跟踪系统（GitHub、Linear，...）** -> 按依赖顺序（阻塞项优先）为每个工单发布一个议题，以便每个工单的阻塞关系可以引用真实标识符。在可用的情况下，为父议题使用平台原生的子议题关系，并为阻塞项使用原生的阻塞关系；否则，将每个工单的“受阻于”设为相应的阻塞议题。除非另有指示，否则应用 `ready-for-agent` 分类标签——这些工单按设计即可由智能体领取处理。
不要关闭或修改任何父议题。
处理**任务前沿**：即阻塞项均已完成的所有工单。对于纯线性链，这意味着从上到下依次处理。
